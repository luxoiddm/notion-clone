# install.md — установка и настройка

## Требования

- Node.js ≥ 18.17
- npm ≥ 10 (в репозитории используются npm workspaces)
- Домен с DNS, указывающим на сервер — нужен для TLS-сертификата (Let's
  Encrypt) и для видеозвонков (TURN поверх TLS использует тот же
  сертификат). Работать по голому IP можно, но без HTTPS браузеры
  блокируют доступ к камере/микрофону почти везде, кроме localhost.
- **nginx** — реверс-прокси перед Node-процессами (шаг 7).
- **coturn** — свой STUN/TURN-сервер для видеозвонков (шаг 8). Не нужен,
  если видеозвонки не используются, либо все звонящие всегда в одной
  локальной сети.
- **PM2** (или другой процесс-менеджер) — держит `apps/server`/`apps/web`
  запущенными и перезапускает при падении (шаг 6). Устанавливается
  отдельно: `npm install -g pm2`.

## 1. Установка зависимостей

```bash
git clone <repo>
cd notion-clone
npm install
```

`apps/server` зависит от `sharp` (ресайз аватаров) — при `npm install`
он докачивает готовый бинарник под платформу сервера (для обычного
Ubuntu x64 — штатно, без доп. действий), так что на этом шаге нужен
доступ в интернет, не только к приватному реестру пакетов, если он у
вас настроен отдельно.

## 2. Настройка `.env`

В проекте два файла окружения — один для сервера, один для веб-приложения.
Скопируй примеры и заполни своими значениями:

```bash
cp apps/server/env.example apps/server/.env
cp apps/web/env.local.example apps/web/.env.local
```

### `apps/server/.env`

| Переменная              | Назначение                                              | Пример                          |
|--------------------------|----------------------------------------------------------|----------------------------------|
| `PORT`                    | Порт, на котором слушает Express + Socket.io             | `4000`                          |
| `WEB_ORIGIN`               | Откуда разрешён CORS (адрес веб-приложения)               | `http://localhost:3000`         |
| `STORAGE_ROOT`             | Путь к папке файлового хранилища — относительный (от `apps/server`) или абсолютный | `./storage`             |
| `ACCESS_TOKEN_SECRET`      | Секрет для подписи access-токенов (JWT, 15 мин)            | случайная строка ≥ 32 символов  |
| `REFRESH_TOKEN_SECRET`     | Секрет для подписи refresh-токенов (JWT, 30 дней)          | **другая** случайная строка     |
| `ADMIN_EMAIL`               | Email первого администратора — создаётся автоматически при старте, пока хранилище пустое | `admin@company.com` |
| `ADMIN_PASSWORD`            | Пароль первого администратора                              | сильный пароль, смени пример!   |
| `ADMIN_DISPLAY_NAME`        | Отображаемое имя первого администратора (необязательно)     | `Администратор`                 |

По умолчанию (`STORAGE_ROOT=./storage`) всё хранилище лежит внутри
проекта — `apps/server/storage/`, а не где-то в системе вроде
`/var/data/...`. Относительный путь резолвится от расположения
`apps/server` (так же, как и сам `.env` — см. раздел «Порты» ниже), а не
от текущей директории запуска, так что это надёжно работает независимо от
того, как процесс-менеджер стартует Node. Можно указать и абсолютный путь
(например, смонтированный отдельный диск в проде) — он используется как
есть, без изменений.

**Переносишь уже работающий проект со старого `STORAGE_ROOT` (например,
с абсолютного системного пути) на новый — данные сами не переедут.**
Скопируй содержимое старой папки в новую вручную перед первым запуском с
обновлённым `.env`:

```bash
cp -r /var/data/storage/* apps/server/storage/
```

Либо просто оставь `STORAGE_ROOT` в `.env` указывающим на старый
абсолютный путь — переменная всё равно настраиваемая, `./storage` это
только дефолт для новых установок.

**`ACCESS_TOKEN_SECRET` и `REFRESH_TOKEN_SECRET` должны быть разными.**
Если использовать один и тот же секрет для обоих токенов, компрометация
одного автоматически компрометирует второй — это одна ошибка вместо двух
независимых рубежей защиты. Сгенерировать пару секретов:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

### `apps/web/.env.local`

| Переменная              | Назначение                                        | Пример                    |
|---------------------------|-----------------------------------------------------|----------------------------|
| `PORT`                     | Порт, на котором стартует Next.js                    | `3000`                     |
| `NEXT_PUBLIC_API_URL`       | Адрес сервера — должен совпадать с `PORT` из `apps/server/.env` | `http://localhost:4000` |

`WEB_ORIGIN` в `apps/server/.env` и `PORT` в `apps/web/.env.local` должны
описывать один и тот же адрес (протокол + хост + порт), иначе CORS будет
отклонять запросы браузера.

## Порты

Next.js читает `.env`/`.env.local` только после того, как его CLI уже
выбрал порт для listener'а (по умолчанию 3000) — записи `PORT=...` в
`apps/web/.env.local` самому Next недостаточно для выбора порта запуска.

Поэтому `apps/web` запускается через `apps/web/scripts/run.mjs`: он
загружает `.env.local` вручную ещё до старта Next.js и передаёт порт
явным флагом (`next dev -p <PORT>` / `next start -p <PORT>`). `npm run
dev` / `npm run start` в `apps/web` уже используют этот скрипт — ничего
дополнительно настраивать не нужно, просто пропиши `PORT` в
`apps/web/.env.local` (не только в серверном `.env`).

Backend (`apps/server`) с портом работает напрямую: Express сам не
выбирает порт заранее, `.env` загружается через `dotenv/config` в самом
начале `src/index.ts`, до вызова `httpServer.listen(PORT)`.

Если порт не применяется:

1. Проверь, что файл называется именно `apps/web/.env.local` (с точкой в
   начале) и лежит на верхнем уровне `apps/web`, а не внутри `app/`.
2. Проверь, что ничего не запускает `next dev` напрямую в обход
   `npm run dev` (например, IDE-конфигурация запуска) — в таком случае
   `run.mjs` не выполнится и порт останется дефолтным.
3. Останови все ранее запущенные процессы Next.js — он умеет автоматически
   занимать следующий свободный порт, если «свой» уже занят, из-за чего
   может казаться, что настройка не сработала.

## 3. Запуск в режиме разработки

Из корня репозитория (запускает `server` и `web` параллельно через
turbo):

```bash
npm run dev
```

Либо по отдельности:

```bash
npm run dev:server   # apps/server, порт из apps/server/.env
npm run dev:web      # apps/web, порт из apps/web/.env.local
```

Проверка, что сервер поднялся:

```bash
curl http://localhost:4000/health
# {"status":"ok"}
```

## 4. Создание первого администратора и остальных пользователей

В системе **нет самостоятельной регистрации** — по требованиям проекта
аккаунт может появиться только определёнными способами.

### 1. Первый администратор — автоматически из `.env`

В `apps/server/.env` есть три переменные:

```env
ADMIN_EMAIL=admin@company.com
ADMIN_PASSWORD=change-me-strong-password
ADMIN_DISPLAY_NAME=Администратор
```

При каждом старте сервер (`seedAdminFromEnv` в
`apps/server/src/routes/auth.routes.ts`, вызывается из `src/index.ts` до
`httpServer.listen`) проверяет: если для `ADMIN_EMAIL` **ещё нет
сохранённых учётных данных** в `STORAGE_ROOT/auth/credentials.json` —
создаёт администратора с этим email/паролем/именем. Если учётные данные
для этого email уже есть (созданы в прошлый раз) — переменные
игнорируются, пароль не перезаписывается и не сбрасывается при
перезапуске. Это же значит: если сменить `ADMIN_EMAIL` на новый адрес и
перезапустить сервер, будет создан **ещё один** администратор с новым
email — старый при этом никуда не денется, его тоже можно удалить или
понизить в роли потом через `/admin`.

То есть сразу после первого запуска (`npm run dev` / `npm run start`)
можно входить на `/` веб-приложения тем email и паролем, что указаны в
`.env`. **Обязательно смени `ADMIN_PASSWORD` на реальный, не оставляй
`change-me-strong-password`** — значение из `.env.example` служит только
примером формата.

Этим же аккаунтом дальше создаются остальные пользователи — см. пункты
2 и 3 ниже. Если что-то пошло не так — раздел «Диагностика входа» ниже.

### 2. Администратор создаёт пользователя напрямую

Требует токен администратора (`Authorization: Bearer <accessToken>`,
получить его — войти на `/` с данными из `.env`, либо через
`POST /api/auth/login`). Сервер сам генерирует временный пароль — его
нужно передать пользователю любым защищённым каналом (в ответе он
приходит один раз, дальше нигде не хранится в открытом виде).

```bash
curl -X POST http://localhost:4000/api/admin/users \
  -H "Authorization: Bearer <ADMIN_ACCESS_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{
    "email": "ivan@company.com",
    "displayName": "Иван Петров",
    "role": "Member"
  }'
```

Ответ:

```json
{
  "user": { "id": "...", "displayName": "Иван Петров", "role": "Member", "createdAt": "..." },
  "temporaryPassword": "aB3xQ9..."
}
```

Пользователь сразу получает личное корневое пространство —
`/{STORAGE_ROOT}/users/{id}/` создаётся автоматически при вызове этого
эндпоинта (см. `FsEngine.createUser()`). Доступные роли: `Admin`,
`Team-Lead`, `Member`, `Guest`.

### 3. Приглашение по ссылке

Альтернатива прямому созданию — сгенерировать ссылку-приглашение и
отправить её пользователю самому (email/Slack), не придумывая пароль за
него:

```bash
curl -X POST http://localhost:4000/api/admin/invites \
  -H "Authorization: Bearer <ADMIN_ACCESS_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{ "email": "maria@company.com", "role": "Team-Lead" }'
```

Ответ содержит `inviteToken` (подписанный JWT, живёт 7 дней) и
`inviteUrl`. Пользователь переходит по ссылке во фронтенде и завершает
регистрацию, отправляя:

```bash
curl -X POST http://localhost:4000/api/auth/accept-invite \
  -H "Content-Type: application/json" \
  -d '{
    "inviteToken": "<TOKEN_ИЗ_ССЫЛКИ>",
    "password": "СвойПароль123!",
    "displayName": "Мария Иванова"
  }'
```

Личное пространство создаётся в этот момент — так же, как и при прямом
создании администратором.

### Запасной вариант: bootstrap-эндпоинт вручную

Если по какой-то причине `ADMIN_EMAIL`/`ADMIN_PASSWORD` не заданы в
`.env`, тот же самый первый администратор создаётся вручную через HTTP —
эндпоинт работает только пока в хранилище нет ни одного пользователя и
сам отключается после первого созданного аккаунта:

```bash
curl -X POST http://localhost:4000/api/auth/bootstrap-admin \
  -H "Content-Type: application/json" \
  -d '{
    "email": "admin@company.com",
    "password": "СложныйПароль123!",
    "displayName": "Главный администратор"
  }'
```

### Важно

- Пароли хранятся как bcrypt-хеш в файле `STORAGE_ROOT/auth/credentials.json`
  (управляется через `FsEngine`, см. `packages/core-fs-engine/README.md`) —
  переживают перезапуск сервера. Ограничь права доступа к `STORAGE_ROOT`
  на уровне ОС (например, `chmod 700`), поскольку это единственный слой
  защиты файла с хешами паролей.
- Понизить/повысить роль себе самому через админ-панель можно, но удалить
  свой собственный аккаунт — нельзя (защита от случайной блокировки
  единственного администратора).
- В админ-панели (`/admin`, доступна только роли `Admin`) можно
  редактировать имя/роль пользователя, сбрасывать пароль (выдаёт новый
  временный пароль) и удалять пользователя целиком — вместе со всеми его
  страницами. Удаление необратимо.

## Диагностика входа («Invalid credentials» и другие проблемы)

Если залогиниться не получается, в этом порядке:

1. **Смотри консоль сервера при старте.** Там всегда печатается: откуда
   загружен `.env`, какой `ADMIN_EMAIL` ожидается, и создал ли
   `seedAdminFromEnv` нового администратора или нашёл уже существующего.
   Пример нормального вывода:
   ```
   [startup] Переменные окружения загружены из /root/wiki1/apps/server/.env
   [startup] PORT=4000  WEB_ORIGIN=https://your-domain.example  STORAGE_ROOT=/root/wiki1/apps/server/storage
   [startup] Ожидаемый администратор из .env: admin@company.com
   [bootstrap] Создан аккаунт администратора для admin@company.com (userId=...), роль Admin.
   ```
   Если вместо этого видно `Учётные данные для ... уже существуют` —
   значит пароль уже был установлен раньше; используй именно тот email,
   который показан в этой строке, либо сбрось пароль скриптом ниже.

2. **Смотри консоль при самой попытке логина.** Каждая неудача
   логируется на сервере с причиной:
   ```
   [auth] Login failed: no credential found for email "admin@company.com"
   [auth] Login failed: wrong password for email "admin@company.com" (userId=...)
   ```
   Первое означает — используешь не тот email, что был засеян; второе —
   email верный, пароль нет.

3. **Проверь `/health` без браузера** — покажет, действительно ли
   `ADMIN_EMAIL` вообще задан на этом сервере:
   ```bash
   curl http://localhost:4000/health
   # {"status":"ok","adminEmailConfigured":true,"webOrigin":"https://your-domain.example", ...}
   ```
   `"adminEmailConfigured": false` — переменные из `.env` не дошли до
   процесса (см. следующий пункт).

4. **Аварийный сброс пароля в обход браузера и HTTP.** Работает всегда,
   если сервер вообще может запуститься (использует тот же `.env` и
   `STORAGE_ROOT`, что и сам сервер — резолвится от расположения файла,
   а не от текущей директории терминала):
   ```bash
   cd apps/server
   npx tsx scripts/reset-admin.ts admin@company.com "НовыйПароль123!" "Администратор"
   ```
   Скрипт выведет, где нашёл (или не нашёл) `.env`, какой `STORAGE_ROOT`
   использует, и создаст пользователя заново или обновит пароль
   существующему — с чёткими сообщениями на каждом шаге. Это самый
   надёжный способ восстановить доступ, если что-то из вышеперечисленного
   не помогло.

5. **Если после curl из пункта 3 `adminEmailConfigured: false`** — сервер
   не находит `.env`. Начиная с этой версии `.env` резолвится по пути
   относительно `apps/server/src/index.ts`, а не от рабочей директории
   процесса, так что при полном обновлении кода это почти всегда чинится
   само. Если нет — проверь, что файл действительно лежит по пути
   `apps/server/.env` (не `apps/server/src/.env` и не в корне репозитория).

## 6. Процесс-менеджер (PM2)

Ручной запуск командой из шага 5 работает, но переживёт только текущую
SSH-сессию — при закрытии терминала процессы Node тоже завершатся, а
при падении (необработанное исключение, нехватка памяти) никто их не
поднимет обратно. Для реального сервера нужен процесс-менеджер.

Готовый конфиг — [`deploy/ecosystem.config.cjs`](./deploy/ecosystem.config.cjs),
запускает оба процесса (`apps/server` и `apps/web`) через `npm run start`
в каждом:

```bash
npm install -g pm2
pm2 start deploy/ecosystem.config.cjs
pm2 save                # чтобы pm2 resurrect восстановил процессы после ребута
pm2 startup             # печатает команду для автозапуска PM2 при перезагрузке ОС — выполни её отдельно, как написано в выводе
```

Полезные команды:

```bash
pm2 status                                     # оба процесса online?
pm2 logs workspace-server                      # логи бэкенда (в т.ч. [startup] строки)
pm2 logs workspace-web
pm2 restart workspace-server workspace-web     # после обновления кода/пересборки
```

## 7. Nginx (реверс-прокси)

Готовый конфиг лежит в [`deploy/nginx.conf`](./deploy/nginx.conf). Он
разводит один домен на два внутренних процесса — Next.js (`apps/web`) и
Express+Socket.io (`apps/server`) — по портам из примеров выше (3000 /
4000; поменяй под свои, если задавал другие в `.env`).

Установка на Ubuntu/Debian:

```bash
sudo cp deploy/nginx.conf /etc/nginx/sites-available/workspace.conf
sudo ln -s /etc/nginx/sites-available/workspace.conf /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

Сертификат (Let's Encrypt / certbot) — стандартно:

```bash
sudo certbot --nginx -d workspace.example.com
```

Что важно поменять в конфиге:

- `server_name workspace.example.com` — на свой домен, в обоих `server`-блоках.
- Пути к сертификатам (`ssl_certificate` / `ssl_certificate_key`), если не
  используешь certbot с автоматической настройкой.
- Порты в `upstream workspace_web` / `upstream workspace_api`, если они
  отличаются от 3000/4000.

**Когда приложение работает за nginx на одном домене, поменяй значения в
`.env` с `localhost:<порт>` на публичный домен**, иначе CORS и cookie
(`secure: true` на refresh-токене) будут работать неправильно:

```env
# apps/server/.env
WEB_ORIGIN=https://workspace.example.com

# apps/web/.env.local
NEXT_PUBLIC_API_URL=https://workspace.example.com
```

REST-запросы из `apps/web/lib/api.ts` идут относительными путями
(`/api/...`) и сами попадут в nginx на том же домене без дополнительной
настройки. `NEXT_PUBLIC_API_URL` в проде нужен только для общего
Socket.io-клиента (`apps/web/lib/socket.ts` — один на presence, чат и
сигналинг видеозвонков) — он должен указывать на тот же публичный
домен, а не на внутренний порт 4000 напрямую, чтобы `wss://` соединение
тоже прошло через `location /socket.io/` в nginx.

## 8. STUN/TURN для видеозвонков (coturn)

Медиапоток (видео/аудио) идёт напрямую между браузерами участников —
сервер в нём не участвует. Но чтобы браузеры вообще нашли друг друга
через NAT (обычный домашний роутер, офисный файрвол — почти всегда),
нужен STUN-сервер, а для части сетей (симметричный NAT, строгие
файрволы) — TURN-сервер, который уже реально ретранслирует медиа через
себя. Публичные STUN/TURN (Google, Twilio и т.п.) — сторонний сервис,
поэтому здесь используется свой: **coturn**, отдельный системный
сервис, не Node-приложение и не npm-пакет.

### Установка coturn

```bash
sudo apt install coturn
sudo cp deploy/turnserver.conf /etc/turnserver.conf
```

Отредактируй `/etc/turnserver.conf`:

- `realm` — на свой домен;
- `static-auth-secret` — случайная строка (`openssl rand -hex 32`),
  **должна буквально совпадать** с `TURN_SECRET` в `apps/server/.env`;
- если есть TLS-сертификат (например, от Let's Encrypt, тот же, что и у
  nginx) — раскомментируй `cert`/`pkey` для `turns://` (TURN поверх TLS).

**Перед первым запуском проверь, что порт `3478` реально свободен** —
если на сервере уже стоит другой WebRTC-сервис со своим встроенным
STUN/TURN (например, [Galene](https://galene.org/) — по умолчанию
слушает `1194`, но нередко его перенастраивают на «стандартный» `3478`,
и тогда конфликт неизбежен):

```bash
sudo ss -tulpn | grep 3478
```

Если порт занят чужим процессом и трогать его не хочется — смени
`listening-port`/`tls-listening-port` в `turnserver.conf` на свободные
(например, `3479`/`5350`) и **пропиши те же значения в
`TURN_PORT`/`TURN_TLS_PORT` в `apps/server/.env`** — coturn не обязан
сидеть строго на 3478, это просто общепринятый дефолт. Заодно сверь
`min-port`–`max-port` ниже с диапазоном медиа-релея другого сервиса,
если он есть — то же самое может незаметно конфликтовать уже на этапе
передачи видео, а не при старте.

Включи автозапуск:

```bash
sudo sed -i 's/#TURNSERVER_ENABLED=1/TURNSERVER_ENABLED=1/' /etc/default/coturn
sudo systemctl enable --now coturn
sudo systemctl status coturn
```

Если сервис не поднимается и в `journalctl -xeu coturn` видно `Address
already in use` — это тот самый конфликт портов выше, а не ошибка в
конфиге; `sudo ss -tulpn | grep <порт>` покажет, какой процесс его
держит.

### Если сервер за NAT/floating IP облачного провайдера — обязательно `external-ip`

Проверить: `curl ifconfig.me` (публичный IP) и `ip -4 addr show | grep
inet` (адрес на самом интерфейсе машины). Если они **разные** — типичная
картина для облака (OpenStack, и не только — у машины приватный адрес
вроде `192.168.x.x`, снаружи виден другой) — без `external-ip` в
`turnserver.conf` звонки будут работать **только между людьми в одной
сети**, а между разными сетями через интернет — нет, без объяснимой на
первый взгляд причины. coturn слышит запросы правильно, но при выдаче
адреса для релея медиапотока сообщает собеседнику свой приватный адрес,
недостижимый снаружи.

Раскомментируй и заполни в `/etc/turnserver.conf`:

```
external-ip=<публичный-IP>/<приватный-IP-этой-машины>
```

Перезапусти `sudo systemctl restart coturn` и проверь звонок заново
между двумя реально разными сетями (не одним Wi-Fi/офисом) — иначе
проблему легко не заметить, локальная сеть её маскирует. Если после
этого всё ещё не работает — следующий подозреваемый уровень: security
group/файрвол самого облачного провайдера (не UFW на машине — у
большинства облаков есть отдельный уровень фильтрации ДО сервера),
может не пропускать снаружи UDP-диапазон `min-port`–`max-port`, даже
если UFW его открывает.

**Открой в файрволе**: порт из `listening-port` (STUN/TURN, UDP и TCP;
`3478` по умолчанию, либо тот, что выбрал выше при конфликте), порт из
`tls-listening-port` (TURN over TLS, TCP, если настроен), и весь
диапазон `min-port`–`max-port` из `turnserver.conf` (по умолчанию
`49152`–`49452`, UDP) — это порты для реально ретранслируемого медиа,
не только сигналинга. Самая частая причина «TURN настроен, но звонки
всё равно не проходят через NAT» — именно забытый файрвол на этом
диапазоне, а не ошибка в конфиге coturn.

### Переменные окружения (`apps/server/.env`)

| Переменная | Назначение | Пример |
|---|---|---|
| `TURN_HOST` | Публичный домен или IP сервера с coturn | `turn.workspace.example.com` |
| `TURN_PORT` | Порт STUN/TURN | `3478` |
| `TURN_TLS_PORT` | Порт TURN поверх TLS (необязательно) | `5349` |
| `TURN_SECRET` | Общий секрет — **тот же**, что `static-auth-secret` в `turnserver.conf` | случайная строка |
| `TURN_CREDENTIAL_TTL_SECONDS` | Срок жизни временных TURN-креды | `3600` |

Сервер никогда не хранит и не выдаёт постоянный TURN-пароль — каждый
клиент при входе в звонок получает свежую пару логин/пароль, срок жизни
которой закодирован прямо в логине (HMAC-подпись общим секретом, без
БД и без отзыва — coturn проверяет сам, ничего не запрашивая обратно у
нашего сервера). Если `TURN_HOST`/`TURN_SECRET` не заданы,
`GET /api/webrtc/ice-servers` честно вернёт пустой список вместо того,
чтобы молча подставить чей-то чужой публичный сервер — звонки при этом
будут работать только между людьми в одной сети или с публичными IP.

## 9. Финальная проверка

Пройдись по списку **на реальном домене** (не `localhost`) — часть
проблем (CORS, `secure`-cookie, WebSocket через прокси) проявляется
только там, локальный `npm run dev` их не покажет:

1. **Backend жив**:
   ```bash
   curl https://workspace.example.com/health
   # {"status":"ok","adminEmailConfigured":true,...}
   ```
2. **Вход** — залогинься под администратором из `.env`. Не получается —
   раздел «Диагностика входа» выше.
3. **Страница и автосохранение** — создай страницу в сайдбаре, напиши
   текст, обнови вкладку (F5). Текст должен сохраниться (автосейв — раз в
   3 секунды после последнего изменения).
4. **Presence** — открой одну и ту же страницу в двух вкладках (или двух
   разных браузерах/аккаунтах) — в шапке редактора должны появиться
   аватарки обоих.
5. **Файлы** — перетащи файл прямо в статью, должен появиться блок с
   картинкой/файлом. Открой `/files` — тот же файл должен быть виден в
   личном хранилище.
6. **Чат** — напиши сообщение (себе через тестовый второй аккаунт, или
   между двумя реальными) — должно прийти без обновления страницы у
   собеседника, с индикатором «печатает...», пока набирается.
7. **Видеозвонок** — начни звонок из чата на одном устройстве,
   присоединись со второго (другой браузер, приватное окно, телефон —
   не то же самое устройство и вкладку). Если чат и текст работают, а
   видео/звук — нет, почти всегда дело в coturn (шаг 8): проверь `sudo
   systemctl status coturn` и что порты (`3478`, диапазон
   `min-port`–`max-port`) реально открыты в файрволе, не только в
   `turnserver.conf`.
8. **Админ-панель** — `/admin` должна открываться и показывать список
   пользователей без `403`.

Если какой-то пункт не проходит — соответствующий раздел ниже («Чат»,
«Видеозвонки» и т.д., либо «Диагностика входа» выше) разбирает его
отдельно и подробнее.

## Админ-панель

Доступна по `/admin`, только пользователям с ролью `Admin` (сервер
проверяет роль независимо от фронтенда — прямой запрос к
`/api/admin/*` без токена администратора получит `403`). Возможности:

- создать пользователя напрямую (сразу получаешь временный пароль);
- отправить приглашение по ссылке;
- изменить имя/роль существующего пользователя;
- сбросить пароль (генерирует новый временный пароль);
- удалить пользователя — необратимо удаляет и все его страницы.

## Расшаренные документы и общая доска

Владелец страницы открывает кнопку **«Поделиться»** в редакторе (видна,
когда открыта своя страница) и выдаёт доступ конкретному пользователю
(`Read`/`Comment`/`Edit`/`Admin`) либо всем по ссылке (только чтение).

Получатель видит расшаренное двумя способами — это один и тот же список,
просто два разных вида:

- прямо в сайдбаре на главной, секцией **«Расшаренные со мной»** под
  собственным деревом страниц — клик открывает документ сразу в основном
  редакторе;
- отдельной полноэкранной страницей **`/shared`** — то же самое, но
  удобнее, если в сайдбаре тесно или страниц много.

В обоих случаях документ открывается в одном и том же редакторе: при
уровне доступа `Edit`/`Admin` — с возможностью редактировать, при
`Read`/`Comment` — в режиме только для чтения (заголовок, текст и кнопки
блоков становятся некликабельными).

## Редактор статей

Блочный редактор (`/`-команды: заголовки, списки, чек-листы, код,
callout, таблица, разделитель, изображение, файл) плюс панель
инлайн-форматирования над текстом статьи — жирный, курсив, зачёркнутый,
код, ссылка. Выделите текст в любом текстовом блоке и нажмите нужную
кнопку в панели сверху.

Вставка изображений и файлов — четырьмя равнозначными способами, все
ведут в одно личное файловое хранилище (см. ниже), поэтому вставленное
можно переиспользовать в других статьях независимо от способа вставки:

- **перетаскивание** файла с компьютера прямо на страницу (можно сразу
  несколько файлов);
- **вставка из буфера обмена** (Ctrl/Cmd+V) — включая скриншот или
  скопированное изображение, а не только текст;
- команда **`/Изображение`** или **`/Файл`** — открывает выбор уже
  загруженного файла или загрузку нового;
- те же две кнопки в панели инструментов над текстом статьи.

Вставка текста из буфера обмена (Ctrl/Cmd+V) сохраняет структуру
исходника — заголовки, списки, цитаты становятся соответствующими
блоками, а не одним куском чужой разметки, с сохранением инлайн-
форматирования внутри них. Работает для двух разных случаев: когда в
буфере есть отрендеренный HTML (обычное копирование с веб-страницы) —
и когда там только голый текст с Markdown-синтаксисом (например,
скопированное из «сырого» просмотра `.md`-файла или из терминала) —
`` # ``, `` **жирный** ``, `` `код` `` и остальные конструкции
распознаются и конвертируются в обоих случаях, а не только когда
источник сам прислал готовую разметку.

## Сайдбар редактора

Сворачиваемая панель справа от статьи (кнопка-переключатель в шапке,
рядом с «Поделиться»). Все четыре секции пересчитываются напрямую из
содержимого документа при каждом изменении, а не хранятся отдельным
состоянием — рассинхронизироваться с самим текстом им попросту нечему:

- **Ярлык** — выбор из 20 стандартных иконок для страницы, плюс
  опционально свои наборы тайлов (см. ниже) — вкладки над сеткой
  переключают между эмодзи и каждым обнаруженным набором.
- **Разделы** — оглавление по заголовкам `H1`/`H2`/`H3` в тексте, клик
  плавно прокручивает к нужному месту в статье.
- **Связанные документы** — ссылки на другие страницы, вставленные
  прямо в текст (кнопка «Ссылка на документ» в тулбаре блока, рядом с
  обычной ссылкой; можно сослаться и на свою, и на расшаренную с вами
  страницу). Появилась ссылка в тексте — появилась в этом списке, без
  ручных действий. Если доступ к документу отозвали уже после того, как
  на него сослались, карточка честно покажет «Нет доступа», а не
  сломается.
- **Теги** — свободный текст, без фиксированного словаря. Добавление —
  Enter или запятая; удаление — крестик на чипе.

### Свои наборы тайлов для ярлыка страницы

Помимо 20 встроенных эмодзи, ярлык страницы можно выбрать из своих
наборов картинок — не через интерфейс приложения, а прямым размещением
файлов на диске сервера, в `storageRoot/tile-sets/`. Два независимых
вида набора, можно использовать любой или оба сразу:

**Спрайт-лист** — один файл `storageRoot/tile-sets/<название>.png`,
сетка по умолчанию **4 столбца × 5 строк**, каждый тайл **64×64
пикселя** (итоговый размер картинки — 256×320). Тайлы вырезаются из
него на лету через `sharp` по номеру (0 — cols×rows-1, слева направо,
сверху вниз). Сетка настраивается через `.env`
(`TILE_SHEET_COLS`/`TILE_SHEET_ROWS`/`TILE_SIZE` в `apps/server/.env`)
— например, если твои спрайт-листы нарезаны на 4×4 по 128×128, а не на
стандартные 4×5 по 64×64. Одна настройка на весь сервер, действует
сразу на все спрайт-листы — разные спрайт-листы с разной сеткой
одновременно не поддерживаются, у всех должна быть одна и та же
раскладка. Изменение требует перезапуска сервера (`pm2 restart wiki1`)
— в отличие от самих файлов наборов, которые читаются заново на каждый
запрос без перезапуска.

**Папка с уже нарезанными тайлами** —
`storageRoot/tile-sets/<название>/`, внутри любое количество отдельных
файлов (`.png`/`.jpg`/`.jpeg`/`.webp`), каждый от **64×64 до 128×128**
— размер не обязан быть одинаковым что внутри одной папки, что между
разными: сам пикер задаёт размер отображения через CSS независимо от
исходного, картинка просто масштабируется. Каждый файл — один тайл;
имя файла (с расширением) становится его идентификатором в URL, так
что стоит держаться простых имён — латиница, цифры, точка, дефис,
подчёркивание. Более сложные имена (с пробелами, кириллицей и так
далее) сервер на диске всё равно найдёт правильно при листинге, но при
самом запросе конкретного тайла проходят через ту же санобработку
имени файла, что и остальные пользовательские пути в приложении — при
не-ASCII символах в имени это может не совпасть с тем, что было в
списке, и тайл не отдастся.

В обоих случаях название файла/папки без расширения становится
названием вкладки в пикере — например, `storageRoot/tile-sets/viking/`
или `storageRoot/tile-sets/viking.png` (но не оба одновременно с
одинаковым именем — при коллизии побеждает спрайт-лист) появятся как
вкладка «viking». Можно разместить сколько угодно наборов любого вида
одновременно.

Ничего перезапускать не нужно — список наборов считывается заново при
каждом открытии пикера (`GET /api/tile-sets`), сами тайлы читаются с
диска на каждый запрос (`GET /api/tile-sets/:setName/:tileId`, обе
публичные, без токена — как логотип сайта: общая картинка, не чьи-то
приватные данные, и ярлык страницы должен быть виден всем, кто видит
саму страницу, а не только её владельцу). Просто изменить файлы на
диске, без перезапуска сервера, чтобы обновить набор.

## Действия с документом (в том же сайдбаре)

Раздел «Действия», под ярлыком:

- **Дочерняя страница** — создаёт новую страницу с текущей в качестве
  родителя и сразу переключает на неё. Доступно только при наличии
  прав на правку — единственная кнопка в этом разделе, требующая их;
  остальные (скачивание, печать) доступны и в режиме только чтения.
- **Скачать .md / .txt** — полностью на клиенте, без обращения к
  серверу (документ уже загружен в редакторе). Markdown сохраняет
  структуру (заголовки/списки/цитаты — по типу блока) и инлайн-
  форматирование (жирный/курсив/ссылки); .txt — только читаемый
  простой текст, без разметки вообще.
- **Скачать .pdf / Печать** — обе кнопки открывают диалог печати
  браузера (`window.print()`), не мгновенное скачивание файла: для
  .pdf в диалоге нужно выбрать «Сохранить как PDF» вместо принтера.
  Осознанный выбор, не ограничение — печатный движок браузера
  справляется со сложным HTML (вложенные списки, изображения, код)
  заметно лучше клиентских PDF-библиотек вроде jsPDF. В печать попадает
  только сам документ — не сайдбары, не шапка, не тулбар редактора, не
  панель комментариев (см. `@media print` в `globals.css`).

## Комментарии к статьям

Под статьёй, внутри той же прокручиваемой области, что и сам редактор —
плоский список (без тредов внутри самого комментария, в отличие от
чата), Markdown, реакции, редактирование/удаление своих. Доступ — по
уже существующему уровню `comment` в правах на страницу (`Доступ к
странице` → «Комментирование»): читать комментарии может любой, кому
доступна страница на чтение, писать и реагировать — от уровня
«Комментирование» и выше, включая «Редактирование»/«Администратор».
Хранятся в той же папке, что и сама страница (`comments.jsonl` рядом с
`meta.json`/`content.json`) — удаление страницы целиком удаляет и её
комментарии автоматически, отдельно чистить не нужно.

## Личное файловое хранилище

У каждого пользователя есть отдельная папка на диске
(`STORAGE_ROOT/users/{userId}/files/`) под файлы, не привязанные к
конкретной статье. Управлять ей можно на странице **`/files`** (ссылка в
шапке главной страницы): загрузить, посмотреть список, скопировать
ссылку, удалить. Те же файлы доступны прямо из редактора через
`/Изображение`/`/Файл` — это одно и то же хранилище, два входа в него.

Ссылка «Скопировать» на странице `/files` содержит короткоживущий
(~15 минут) токен доступа в URL — годится, чтобы вставить в документ,
который редактируете прямо сейчас, но не как постоянная публичная
ссылка. Откройте `/files` заново, если ссылка понадобится позже — она
скопируется со свежим токеном.

## Чат

Страница **`/chat`** (ссылка в шапке главной страницы) — личные и
групповые беседы:

- **«+» в шапке списка чатов** — открывает диалог создания. Личный чат:
  выбор собеседника из справочника пользователей; повторный выбор того
  же человека открывает уже существующий диалог, а не создаёт новый.
  Групповой: мультивыбор участников + необязательное название (если не
  задать — группа называется по именам участников).
- Сообщения доставляются живьём через сокеты, без обновления страницы;
  видно, когда собеседник печатает.
- **Треды** — клик на «Ответить в теме» под сообщением разворачивает
  ветку ответов снизу, со своим полем ввода.
- **Скрепка** в поле ввода прикрепляет ссылку на одну из ваших страниц —
  можно отправить и без текста, одной ссылкой. Получатель видит карточку
  с заголовком (если у него есть доступ к документу — иначе честно
  «Нет доступа», без утечки названия) и может открыть её прямо в
  редакторе кликом.

Чат не заменяет уведомления — если собеседник не в сети, сообщение всё
равно сохранится и будет ждать его в списке чатов при следующем входе.

## Видеозвонки

Личные и групповые звонки прямо в чате — до 8 участников, mesh-топология
(каждый участник соединяется с каждым напрямую, сервер видео не видит).
Настройка своего STUN/TURN-сервера (coturn) — отдельный шаг при
установке, см. «Шаг 8. STUN/TURN для видеозвонков» выше; без него
звонки работают только между людьми в одной сети или с публичными IP.

- **«Начать звонок»** в шапке открытого чата — запрашивает доступ к
  камере/микрофону и подключается. Повторный клик по тому же чату
  присоединяется к уже идущему звонку (эндпоинт идемпотентный), а не
  создаёт новый.
- Остальные участники чата видят баннер **«Имя звонит»** внизу экрана —
  независимо от того, какая страница у них сейчас открыта, не только
  если окно чата открыто. Кнопка «Присоединиться» ведёт прямо в этот чат
  с уже начатым подключением.
- Контролы под сеткой видео: вкл/выкл микрофона, вкл/выкл камеры,
  демонстрация экрана. Остановить показ экрана можно как своей кнопкой,
  так и нативной кнопкой браузера «Остановить показ» — оба способа
  приводят к одному и тому же.
- Один активный звонок на пользователя одновременно — попытка начать
  звонок в другом чате, пока уже идёт этот, покажет неактивную кнопку с
  подсказкой «Сначала завершите текущий звонок».

## Настройки профиля

Страница `/settings` (ссылка — клик по своему аватару в шапке главной
страницы):

- **Аватар** — кружком, отовсюду (шапка, presence, авторы сообщений в
  чате). Выбор через тот же диалог, что и вложения в чате/редакторе —
  можно взять уже загруженный файл или загрузить новый. Хранится **в
  личном файловом хранилище пользователя** (`/files`), не в отдельной
  структуре — как обычный личный файл, просто на него ссылается профиль.
  Автоматически обрезается под квадрат и уменьшается до 256×256 (WebP,
  несколько КБ) — исходник с телефона в несколько мегабайт не хранится
  как есть.
- **Акцентный цвет** — 8 приглушённых пресетов, красят кнопки, ссылки и
  свои сообщения в чате по всему приложению сразу при выборе, без
  перезагрузки страницы. Это личная настройка «моего интерфейса» — не
  меняет, каким цветом видят *ваши* сообщения другие, только то, каким
  цветом *вы* видите акцентные элементы у себя.

## Настройки сайта (админ-панель)

Раздел «Настройки сайта» в `/admin`, доступен только Admin:

- **Название, описание, копирайт** — применяются везде: заголовок
  вкладки браузера, экран входа, шапка сайдбара. Копирайт — на экране
  входа и в настройках профиля.
- **Два независимых логотипа**, не один переиспользуемый — для экрана
  входа (крупный, показывается один раз на весь экран) и для шапки
  сайдбара (маленький, в каждой строке). Логотип, который хорошо
  читается на весь экран, часто превращается в кашу при уменьшении до
  строки сайдбара — поэтому это два отдельных изображения, каждое со
  своей загрузкой в форме. Загружаются отдельно от аватаров, не в личное
  хранилище (это общесайтовый ресурс, не персональный) — своя выделенная
  область хранения, перезаписывается при каждой замене, версии не
  хранятся. Вписываются в рамку 512×512 с сохранением пропорций (не
  обрезаются под квадрат, как аватар) и прозрачности (WebP, логотипы
  часто на прозрачном фоне).
- **Размер отображения** каждого логотипа (в пикселях, не размер файла)
  — через `NEXT_PUBLIC_LOGIN_LOGO_HEIGHT`/`NEXT_PUBLIC_HEADER_LOGO_HEIGHT`
  в `apps/web/.env.local` (дефолты — 64 и 32). Как и всякая
  `NEXT_PUBLIC_*`-переменная, вшивается на этапе сборки — на
  production-сборке (`next build`) для применения нужна пересборка, на
  `next dev` подхватывается при следующем перезапуске.
- Название/описание/логотипы видны **до входа в систему** — экран логина
  их запрашивает без токена авторизации. Единственный по-настоящему
  публичный (без проверки токена) эндпоинт во всём проекте —
  `GET /api/site-settings` — осознанное исключение, а не недосмотр:
  иначе экран логина нечем было бы их показать.
