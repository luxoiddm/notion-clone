## [1.51.2] — 2026-10-06

### Исправлено
- Удаление голосового или кружка из чата теперь удаляет и сам файл из каталога автора (если он больше нигде не используется). При запуске сервер один раз убирает записи, оставшиеся от сообщений, удалённых раньше.
- При удалении любого сообщения с вложением участники чата теряют доступ к файлу (ссылка из индекса использования убирается). Обычный файл из «Файлов» остаётся у владельца.

## [1.51.0] — 2026-10-06

### Добавлено

- Вложение сообщения получило поля `kind` (voice / round), `duration`, `waveform`; сервер проверяет их и разрешает такие записи независимо от `CHAT_ALLOWED_MIME_TYPES`.

## [1.50.0] — 2026-10-06

### Добавлено

- **Файловый менеджер в админке** («Администрирование → Файлы»,
  `components/AdminStorage.tsx`, `/api/admin/storage/*`): таблица
  пользователей с числом файлов/документов, занимаемым местом и путём к
  папке на диске; каталог пользователя — файлы (скачать, просмотр,
  перенести другому пользователю, удалить, массовые действия, где
  используется) и документы (открыть, удалить).
- **Перенос файла** между каталогами (`FsEngine.moveUserFile`): файл и
  запись манифеста переезжают, ссылки в страницах переписываются через
  `savePageContent`, во вложениях чатов — `ChatEngine.replaceAttachmentUrl`
  (+ `chat:message-updated`), публичная ссылка `/f/…` сохраняется.
- **Увольнение**: `POST /api/admin/users/:id/dismiss` / `restore` — папка
  целиком переезжает в `STORAGE_ROOT/dismissed/{id}` (и обратно), вход
  запрещён. Все пути к данным пользователя теперь строятся через
  `userRoot()`, поэтому документы, файлы, общий доступ и публикации
  уволенного продолжают работать без переписывания ссылок. Уволенные
  скрыты из выбора коллег (`dismissed` в `/api/users`), не добавляются в
  чаты.
- `STORAGE_ROOT/USERS.txt` — человекочитаемый список папок: путь → имя,
  email, статус (обновляется при изменениях и на старте).
- Администратор может открыть любой файл личного хранилища (для
  скачивания из файлового менеджера).

### Изменено

- «Удалить пользователя» теперь «Удалить полностью» с подтверждением
  вводом слова; удаляет также публичные ссылки на его файлы и записи в
  индексе использования. Рядом — «Уволить» / «Вернуть».

## [1.46.1] — 2026-10-02

### Безопасность

- **Ссылка на файл из адресной строки открывалась в инкогнито.** К
  адресам картинок и файлов (`<img src>`, «открыть») добавлялся `?token=`
  с access-токеном, и скопированный URL работал у любого ~15 минут.
  Теперь браузер авторизует медиа httpOnly-cookie `mediaToken` (ставится
  в login/refresh/accept-invite, удаляется в logout; принимается только
  для GET/HEAD), `requireAuth` больше не читает `?token=`,
  `withAuthToken()` возвращает адрес как есть. Без входа прямая ссылка
  показывает страницу «Войдите в систему» (401).

### Добавлено

  вместо новой вкладки: картинки, PDF, видео, аудио, текстовые файлы;

### Исправлено

- PDF отдаётся без sandbox-CSP, чтобы встроенный просмотрщик открывал

- После возвращения во вкладку (>5 мин в фоне) токен обновляется сразу —
  чтобы картинки не перестали грузиться.

## [1.46.0] — 2026-10-02

### Безопасность

- **Файлы личного хранилища открывались без входа по прямой ссылке.**
  Кнопка «Скопировать ссылку» на `/files` вшивала в URL `?token=` с
  токеном доступа, и такой адрес работал у любого, кто его получил.
  Теперь `GET /api/files/serve/:userId/:fileName` проверяет права:
  владелец, выданный доступ (конкретным людям или `*` — всем сотрудникам),
  читатели страницы, в которую вставлен файл (для одобренных публичных
  страниц — и аноним), участники чата с этим вложением, текущий аватар
  владельца. Без входа — 401, без права — 403. Токен в копируемые
  ссылки больше не добавляется.
- Файлы отдаются с `X-Content-Type-Options: nosniff` и sandbox-CSP —
  загруженный HTML/SVG не выполняется в контексте сайта.

### Исправлено

- **Кириллица в именах файлов.** multer декодировал имя как latin1
  («ÐÑÑ‡ÐµÑ‚»), а затем `sanitizeFileName` заменял не-ASCII на `_`.
  Имя теперь перекодируется в UTF-8 (`apps/server/src/lib/uploadName.ts`,
  и для файлов хранилища, и для вложений страниц), хранится как есть в
  манифесте (`sanitizeDisplayFileName`), а на диске файл лежит под
  ASCII-именем `{timestamp}-{id}.{ext}`. Скачивание отдаёт исходное имя
  (`Content-Disposition: filename*=UTF-8''…`). Уже испорченные имена
  восстановить нельзя.

### Добавлено

- **Доступ к файлам для коллег**: диалог «Доступ и ссылки» на карточке
  файла — выбор сотрудника или «Все сотрудники», список с аватарами,
  закрытие доступа. Вкладка «Доступные мне» на `/files`.
  `PUT /api/files/:fileName/sharing`, `GET /api/files/shared`.
- **Публичная ссылка** `/f/{token}` — проксируется сервером, не раскрывает
  владельца и путь к файлу, работает без входа, отзывается владельцем.
  `POST|DELETE /api/files/:fileName/public-link`, публичный
  `GET /api/public-files/:token` (rewrite `/f/:token` в next.config.js).
- Кнопка «Скачать» (`?download=1`) и «Внутренняя ссылка» (без токена).
- Индекс использования файлов `STORAGE_ROOT/file-refs.json` (страницы и
  чаты), строится при первом запуске по всем страницам и вложениям.

## [1.31.1] — 2026-09-01

### Исправлено

- **Неправильное форматирование блоков кода на публичной странице
  (и в истории версий) — сырой HTML показывался как текст.** Реальная

  `code`, рендерится через `dangerouslySetInnerHTML`, как все
  остальные типы блоков. Заодно добавлен `whitespace-pre-wrap`,

## [1.29.3] — 2026-08-31

### Исправлено — критично

- **Найдена настоящая причина, по которой публикация страниц вообще не
  работала: сервер физически не мог собраться.** Все проверки `tsc` в
  ходе разработки этой сессии запускались на отдельных файлах с
  урезанными флагами — это НЕ то же самое, что настоящая сборка
  проекта (`tsc -p tsconfig.json`, с реальным `noUncheckedIndexedAccess:
  true` и полным резолвом типов воркспейса). Пользователь прислал
  реальный вывод `npm run build` — 85 ошибок типов. Воспроизведено
  точно: `req.params.xxx` в Express типизируется как `string |
  undefined`, не `string`, из-за индексной сигнатуры типа `req.params`
  и строгого флага в `tsconfig.base.json`. Касалось ВСЕГО кодового
  пространства, не только публикации страниц — `storage.routes.ts`
  (48 ошибок сам по себе, файл существовал задолго до этой сессии),
  `chat.routes.ts` (19), `admin.routes.ts`, `files.routes.ts`,
  `tileSets.routes.ts`. Раз сборка сервера падала, `pm2 restart` все
  эти версии просто продолжал крутить старую, уже собранную версию —
  без единого явного сообщения об этом на этапе перезапуска. Починено
  во всех местах разом — `req.params.xxx!` (non-null assertion сразу
  после имени параметра), безопасно ровно потому, что Express
  гарантирует наличие параметра, если маршрут вообще совпал по
  паттерну.
- Заодно — при переходе на настоящую сборку `apps/web` (`tsc -p
  tsconfig.json`, отдельно от `next build`) нашлось ещё две реальные
  ошибки типов, тоже никогда не ловившиеся изолированной проверкой
  файлов: собственный упрощённый тип `React.ComponentType<{size?:
  number}>` для иконок в `Editor.tsx`/`SlashMenu.tsx` был не совместим
  с точным типом `lucide-react` при установленной версии
  `@types/react` — заменено на настоящий `LucideIcon` из пакета;
  ref-колбэк в `Sidebar.tsx` (`ref={(el) => el && setViewportHeight(...)}`)
  мог формально вернуть `null` вместо `void` — обёрнуто в блок с `if`.
- Диагностическое логирование, добавленное в 1.29.2 для поиска этой
  проблемы, убрано — причина найдена и никак не связана с логикой
  самого кода отправки/чтения заявок (та была написана верно с самого
  начала, просто никогда не компилировалась).

## [1.29.0] — 2026-08-31

### Добавлено

- **Публичные страницы** — курируемые администратором деревья
  документов, собранные из личных страниц разных пользователей,
  доступные без входа в систему по адресу `/<slug>`. Полный цикл:
  админка создаёт/включает/выключает страницу → любой пользователь с
  правом на редактирование отправляет свой документ на публикацию
  (кнопка-глобус в правой панели редактора) → администратор
  одобряет/отклоняет в очереди модерации, с необязательной причиной
  отклонения → одобренные документы выстраиваются в собственное дерево
  (независимое от структуры у автора — смена родителя, порядок,
  удаление узла) → страница доступна анонимно по адресу. Отправка
  ранее отклонённого документа возвращает его в очередь модерации, не
  создаёт дубликат. Слаг публичной страницы не может совпадать с уже
  занятыми путями приложения (`admin`, `chat`, `files`, `settings`,
  `shared`, `api`) — иначе страница физически была бы недостижима,
  Next.js всегда отдаёт предпочтение точному совпадению маршрута перед
  динамическим.
- **Переход в редактирование прямо с публичной страницы** — если
  текущий посетитель (авторизованный в том же браузере) является
  автором документа или имеет право на его редактирование, у статьи
  появляется кнопка «Редактировать». Публичный роут для этого не
  требует авторизации — токен передаётся, только если человек и так
  уже вошёл в систему в этом браузере, отсутствие или недействительность
  токена не считается ошибкой, посетитель просто не видит кнопку.
  Повторная модерация после правки — не новый отдельный механизм, та
  же самая отправка на публикацию, что уже сбрасывает одобренный узел
  обратно в очередь при повторной отправке того же документа.

### Известно, но не подтверждено

- Есть отзыв, что отправленный документ иногда не появляется в очереди
  модерации. Сквозная проверка кода (порядок регистрации роутов, тело
  запроса, доступ к файлу заявок) не выявила определённой причины —

  защиты: превентивный таймер в `SessionProvider` (обновляет каждые 12

  придерживает `setInterval` у неактивных вкладок). Обновление токена
  дедуплицировано (`refreshAccessToken()`, общая на весь клиент) — если
  несколько запросов одновременно словят 401, обновление токена
  запросится один раз, не по одному на каждый.

  мобильном, что перекрывает шапку целиком по всей высоте вьюпорта,
  независимо от порядка в DOM (`fixed` позиционируется от вьюпорта, не
  от родителя, в котором лежит). Оверлей и его бэкдроп у обоих теперь
  начинаются ниже шапки (`top-12`), не перекрывая её содержимое.
- **Заголовок документа мог потеряться при быстрой навигации сразу
  после редактирования** — найдено по ходу, отдельная причина той же
  жалобы. У контента страницы уже был flush отложенного сохранения при
  размонтировании/смене страницы, у заголовка (отдельный дебаунс) —
  не было, хотя докстринг утверждал обратное. Добавлена такая же
  защита, срабатывает только если реально было отложенное сохранение
  (не на каждое переключение страниц просто так).
- **Обновление страницы (F5) сбрасывало в начальное состояние** — как в
  редакторе, так и в чате. Открытая страница/чат хранились только в
  клиентском состоянии (Zustand/`useState`), не отражались в URL,
  поэтому у полной перезагрузки не было способа понять, что
  восстанавливать. Редактор теперь синхронизирует `?owner=&project=
  &page=` с открытой страницей; у чата уже был частичный механизм
  (`?open=<chatId>` для deep-link из уведомления о входящем звонке), но
  только на чтение — добавлена запись в обратную сторону при обычном
  клике по чату в списке, не только через deep-link. Оба — через
  `router.replace`, не `push`, чтобы переключение между страницами/
  чатами не засоряло историю браузера записью на каждый клик.

### Добавлено

  монтирует новый, пустой; раз при конвертации типа с сохранением

  типа блока с сохранением содержимого вообще, вставка просто оказалась

  уходят по одному, у оставшихся звонок продолжается, и только когда

  начала, просто нечем было её менять). `FsEngine.updatePageIcon()` —

### Изменено

- **Чат — отправка по Ctrl+Enter вместо просто Enter** (во всех трёх
  местах: основной композер, ответ в теме, редактирование сообщения) —
  просто Enter теперь просто перенос строки, ничего не отправляет.
  Раньше Shift+Enter был единственным способом перенести строку, что
  неудобно для длинных многострочных сообщений — набирать текст,
  постоянно держа Shift, но рискуя случайно отправить недописанное
  простым Enter. Подсказки в плейсхолдерах и рядом с кнопкой
  «Сохранить» при редактировании обновлены.
- **Настоящее удаление сообщений вместо плейсхолдера «Сообщение
  удалено»** (отзыв после реального использования). Раньше удаление
  было всегда мягким — сохраняло строку с очищенным содержимым,
  специально ради того, чтобы ответы в треде не потеряли, на что они
  отвечали. Теперь удаление по умолчанию **настоящее** (строка
  полностью убирается из хранилища) — мягкое поведение с плейсхолдером
  осталось только как редкий fallback, когда у сообщения **уже есть**
  ответы в треде (иначе они стали бы физически недостижимы — кнопка
  треда живёт на корневом сообщении). Новое realtime-событие
  `chat:message-deleted`, отдельное от `chat:message-updated` — для
  полностью убранного сообщения нет объекта `ChatMessage`, который можно
  было бы разослать, только `messageId`.
- **Убрана непонятная горизонтальная прокрутка в блоках кода чата.**
  `<pre>` в браузере по умолчанию не переносит строки (`white-space:
  pre`), и это в сочетании с `overflow-x: auto` требовало прокрутки
  даже для короткого однословного «кода» в узком пузыре сообщения —
  что для чата (не редактора кода) неуместно. Переключено на
  перенос строк (`white-space: pre-wrap` + `word-break`) — длинные
  токены без пробелов (хеши, длинные слова) переносятся, а не вылезают
  за пределы пузыря и не требуют скролла.
- **Поле редактирования сообщения растёт по содержимому**, а не
  зажато в фиксированные 2 строки — редактировать длинное сообщение
  было неудобно, весь текст не помещался в маленькое окошко.

- **Логотип разделён на два независимых изображения** — для экрана
  входа и для шапки сайдбара, вместо одного переиспользуемого. Логотип,
  который хорошо читается на весь экран, часто превращается в кашу при
  уменьшении до 32px строки сайдбара — разные контексты отображения
  нуждаются в разных изображениях, не в одном масштабируемом. Модель
  данных: `SiteSettings.logoUrl` → `loginLogoUrl`/`headerLogoUrl`, с
  нормализацией старых записей (`getSiteSettings()` подставляет старое
  значение `logoUrl` в оба новых поля, если они ещё не заданы — логотип,
  загруженный до этого разделения, не пропадает из обоих мест сразу).
  Хранение и раздача параметризованы видом (`saveSiteLogo(kind, ...)`,
  `GET /api/site-settings/logo/:kind`), загрузка в админке — два
  отдельных поля вместо одного.
- **Размер логотипов вынесен в `.env`** —
  `NEXT_PUBLIC_LOGIN_LOGO_HEIGHT`/`NEXT_PUBLIC_HEADER_LOGO_HEIGHT`
  (дефолты 64/32), вместо зашитых в код Tailwind-классов. Валидация
  вручную (`Number.isFinite && > 0`), а не голый `??` — пустая строка в
  `.env` не даёт `Number('')` тихо превратиться в 0px логотип.
- **Логотип на экране логина теперь по центру**, а не прижат к левому
  краю формы (`<img>` — инлайн-элемент по умолчанию, без явного
  центрирования просто наследовал выравнивание текста).

  markdown-синтаксис перед вставкой, так что форматирование переживает
  путь через голый текстовый композер и корректно отрисовывается при
  показе сообщения. Вставка обычного текста/готового markdown-синтаксиса

- **Отправка сообщения не обрабатывала ошибку вообще.** С появлением

  сообщением, теперь в одной всплывающей при наведении панели сверху

- **Всплывающая панель выбора эмодзи улетала за край экрана.** Была
  жёстко приклеена к левому краю кнопки (`left-0`, разворачивается
  вправо) — на своих (выровненных по правому краю) сообщениях кнопка
  сама оказывается у правого края окна чата, и панель, разворачиваясь
  ещё правее, вылезала за видимую область. Теперь сторона разворота
  зависит от того, чьё это сообщение: у своих — `right-0` (разворот
  влево), у чужих — `left-0` (разворот вправо, как и было, там места
  достаточно).

- **Краш чата на старых сообщениях: `Cannot convert undefined or null to
  object`** (найдено на реальном использовании). Сообщения, отправленные
  до появления `editedAt`/`deletedAt`/`reactions` (этап 2 доработки
  чата), в файле хранятся без этих полей вообще — `JSON.parse` и
  `as ChatMessage` тому не мешают, это чисто компайл-тайм утверждение,

  `ChatEngine` теперь нормализует каждое прочитанное сообщение
  (`normalizeMessage()`), подставляя дефолты для отсутствующих полей,
  а не только в момент чтения одного конкретного места, где произошёл
  краш — так что старые данные корректно доотображаются везде, не только
  там, где заметили. Плюс защитный фолбэк `?? {}` в самом компоненте на
  случай непредвиденного пути данных без нормализации.

### Добавлено

- **Чат, этап 4 — реакции на сообщения.** Небольшой фиксированный набор

  ради этого) — кнопка появляется при наведении на **любое** сообщение

- **Чат, этап 3 — редактирование и удаление на фронтенде.** Кнопки
  «Редактировать»/«Удалить» видны при наведении, только на своих
  сообщениях. Редактирование — инлайн `textarea` прямо в пузыре

  отмена), рядом с временем появляется «(изменено)». Удаление —
  подтверждение через `confirm()`, тот же паттерн, что уже используется

  плейсхолдер «Сообщение удалено» вместо содержимого. Правки долетают
  живьём через новое событие `chat:message-updated` из прошлого этапа —
  реализована и замена по id в основной ленте, и в открытом треде
  (правки не знают заранее, где именно показано затронутое сообщение).
  Отдельно поправлено: если у удалённого сообщения уже были ответы в
  треде, кнопка треда всё равно остаётся видна — иначе эти ответы стали
  бы недостижимы через интерфейс, что как раз и было причиной делать
  удаление мягким, а не физическим. Превью последнего сообщения в
  списке чатов тоже учитывает удаление (раньше показало бы пустую
  строку вместо текста).

- **Чат, этап 2 — бэкенд для редактирования, удаления, реакций.**
  `ChatEngine.editMessage`/`deleteMessage` — только автор сообщения
  (проверка `authorId`, иначе исключение → 403), `toggleReaction` —
  любой участник чата, повторная реакция тем же эмодзи снимает её.
  Удаление — мягкое (`deletedAt` + очистка текста/вложений/реакций,
  сама строка остаётся, чтобы ответы в треде не потеряли, на что они
  отвечали). Хранилище сообщений — append-only JSONL, но
  редактирование/удаление/реакция — по природе read-modify-write
  (прочитать файл целиком, заменить одну строку, переписать обратно
  атомарно через временный файл); чтобы это не рассинхронилось с
  обычной отправкой сообщения (`sendMessage` раньше просто дописывала
  файл без блокировки), все операции над файлом чата — включая
  добавление — теперь идут через общую блокировку по пути файла
  (`lockManager.ts`, самодостаточная копия версии из `@core/fs-engine`
  — не тащить весь пакет ради 30 строк общей логики). Новое realtime-
  событие `chat:message-updated`, отдельное от `chat:message` — правки
  существующего сообщения нельзя доставлять тем же событием, что и
  новые: фронтенд трактует `chat:message` как «добавить, если ещё нет»
  с дедупликацией по id, так что повтор через него просто молча
  проигнорировался бы как «уже есть». Новые роуты: `PATCH`/`DELETE
  /:chatId/messages/:messageId`, `POST
  /:chatId/messages/:messageId/reactions`. Фронтенд — следующий этап.

### Безопасность

- **XSS через ссылку в Markdown-тексте (`[текст](url)`).** Найдено при
  реализации markdown-рендера в чате. `inlineMarkdownToHtml()`
  (используется и вставкой сырого markdown в редакторе, и теперь чатом)
  собирала `href`-атрибут прямой конкатенацией строк; `escapeToHtml()`
  экранирует `&`/`<`/`>` — достаточно для текстового содержимого, но не
  для значения HTML-атрибута, где дополнительно нужно экранировать
  кавычки. Ссылка вида `[x](http://e.com" onmouseover="…)` вырывалась из
  `href="..."` и внедряла произвольный обработчик события — рабочий
  stored-XSS для любого, кто откроет документ/сообщение с таким текстом.
  Проверка на `javascript:`/`data:`-схемы (по префиксу) эту дыру не
  закрывала — она не проверяет остальную часть строки. Не была
  единственной линией защиты в конвейере — при вставке markdown в
  редакторе результат `inlineMarkdownToHtml()` не проходит повторную
  санитизацию перед сохранением в блок, так что уязвимость была реальной,
  не перекрытой ничем ещё. Путь через живой набор в редакторе
  (`Editor.tsx`, DOM `setAttribute('href', …)` вместо сборки строки) этой
  проблеме не подвержен в принципе — `setAttribute` не парсит значение
  как HTML. Исправлено экранированием кавычек непосредственно перед
  вставкой в атрибут.

- **Видеозвонки, этап 5 — демонстрация экрана.** Замена исходящего
  видео-трека через `RTCRtpSender.replaceTrack()` у всех уже
  подключённых пиров разом — без пересоздания соединений и без
  повторного SDP-обмена, поскольку видео-`m-line` не меняется, меняется
  только то, какой трек его наполняет. Кнопка в `CallControls` и
  собственная реакция на нативную кнопку «Остановить показ» браузера
  (`track.onended`) — оба пути ведут в одну и ту же функцию остановки, не
  два похожих. Участник, присоединившийся уже во время демонстрации,
  сразу получает трек экрана, а не камеры — иначе ему потребовалась бы
  секунда до следующего `replaceTrack()`, чтобы догнать остальных.
  Полностью останавливается вместе с выходом из звонка (`teardown` теперь
  освобождает и поток экрана, не только камеру/микрофон) — камера/микрофон
  светодиод гаснет полностью, ничего не остаётся висеть в фоне.

- **Видеозвонки, этап 4 — оповещение о входящем звонке.** Каждый сокет
  теперь автоматически вступает в свою личную комнату (`personalRoomKey`
  в `@core/realtime`, `user:{id}`) сразу при подключении — общий примитив
  «достучаться до конкретного пользователя независимо от того, что у
  него сейчас открыто», не только для звонков. При *первом* создании
  комнаты (не при повторном idempotent-вызове `call:start` — иначе
  каждый рейджойн спамил бы всех заново) сервер рассылает `call:incoming`
  всем остальным участникам чата через их личные комнаты. `CallProvider`
  слушает это глобально (провайдер один на всё приложение — см. этап 2),
  `IncomingCallBanner` смонтирован в layout рядом с провайдером и виден
  на любой странице, не только внутри открытого окна чата. Кнопка
  «Присоединиться» переиспользует тот же `startOrJoinCall`, что и ручной
  запуск звонка (никакого отдельного пути входа), и ведёт на
  `/chat?open=<chatId>` — страница чата теперь читает этот параметр и
  сама открывает нужную беседу.

  примерно квадратная раскладка, как в большинстве видеоконференций),
  строится поверх того же состояния из этапа 2 без изменений в
  протоколе. `CallControls` — вкл/выкл микрофона и камеры, завершение

### Добавлено

- **Действия над выделенным диапазоном блоков.** Delete/Backspace удаляют
  весь диапазон разом (с той же защитой от опустошения документа

  `text/plain` как запасной вариант. Двухступенчатый Ctrl+A, как в

  происходит само по себе (браузер это умеет бесплатно), но при повторном
  нажатии, когда блок уже выделен целиком, редактор перехватывает и
  расширяет выделение на весь документ через тот же механизм диапазона
  блоков.

- **Выделение диапазона блоков мышью (как в Asana/Notion).** Браузер
  физически не умеет тянуть нативное текстовое выделение через границу
  двух разных `contentEditable`-блоков — это ограничение платформы, не
  наше. При перетаскивании мыши из одного блока в другой редактор сам
  ловит момент пересечения границы, сбрасывает уже начавшееся частичное
  нативное выделение и переключается в отдельный режим — целиком
  выбранные блоки подсвечиваются (работает и для картинок/файлов/
  разделителя, которые вообще не редактируемы напрямую). Shift+клик по
  блоку расширяет диапазон от последнего сфокусированного блока.
  Выделение сбрасывается по Escape, началу печати или обычному клику.
  Технически: детект через `document`-level `mousemove`/`mouseup`
  слушатели (не per-блок), проверяющие `data-block-row-id` под курсором,
  а не отдельная HTML5 drag-and-drop механика — не пересекается с уже
  существующим перетаскиванием блоков за ручку (это два разных набора
  событий браузера). Действия над выделенным диапазоном (удаление,
  копирование, `Ctrl+A`) — предмет следующего этапа.

- **Инструмент реального контроля синтаксиса.** Обнаружился глобальный
  `tsc` в среде разработки — с этого раунда синтаксис проверяется им

- **Markdown-автоформат, этап 2 — инлайн-форматирование.** `**текст**` →
  жирный, `*текст*`/`_текст_` → курсив, `` `текст` `` → инлайн-код,

  `<img src>`/`<a href>` не смогли бы аутентифицироваться (браузер не
  посылает кастомные заголовки для таких запросов). Используется
  `apps/web/lib/api.ts:withAuthToken()` везде, где строится URL картинки
  или файла.
- **Админ-панель** (`/admin`, только роль `Admin`): список пользователей,
  создание, редактирование имени/роли, сброс пароля, удаление,
  приглашения по ссылке. Бэкенд: `GET/PATCH/DELETE /api/admin/users`,
  `POST /api/admin/users/:id/reset-password`.
- **Страница «Расшаренные со мной»** (`/shared`): список всех страниц, к
  которым другим пользователям открыт доступ; открытие документа ведёт в
  основной воркспейс (см. запись про общее дерево выше), а не в
  отдельный вьюер. Бэкенд: `GET /api/shared`, `FsEngine.listSharedPages()`.
- **Диалог «Поделиться»** в редакторе — выдача/отзыв доступа конкретному
  пользователю или всем по ссылке. Бэкенд:
  `PUT /api/storage/:userId/:projectId/pages/:pageId/sharing`,
  `FsEngine.updatePageSharing()`.
- `GET /api/users` — минимальный справочник пользователей (id + имя, без
  email/роли) для диалога «Поделиться» и подписи владельца в
  «Расшаренные со мной».
- `GET /api/auth/me` + `SessionProvider`
  (`apps/web/components/SessionProvider.tsx`) — восстановление сессии по
  httpOnly refresh-cookie при жёсткой перезагрузке страницы или открытии
  `/admin`/`/shared`/`/files` в новой вкладке, вместо мгновенного
  возврата на экран входа.
- `apps/server/scripts/reset-admin.ts` (`npm run admin:reset-password -w
  apps/server`) — аварийное создание/сброс пароля администратора в обход
  HTTP и браузера, напрямую через `FsEngine`/`AuthService` с тем же
  `.env` и `STORAGE_ROOT`, что использует сам сервер.
- `ADMIN_EMAIL` / `ADMIN_PASSWORD` / `ADMIN_DISPLAY_NAME` в
  `apps/server/.env` — сервер сам создаёт первого администратора при
  старте (`seedAdminFromEnv`), если для этого email ещё нет учётных
  данных. Раньше единственным способом было вручную дёргать
  `/api/auth/bootstrap-admin` — этот эндпоинт остался как запасной
  вариант.
- `deploy/nginx.conf` — конфиг реверс-прокси для продакшена: один домен,
  роутинг на `apps/web` (Next.js) и `apps/server` (Express), отдельный
  `location /socket.io/` с апгрейдом до WebSocket для presence/курсоров/
  сигналинга звонков, `location /health` для проверки живости API.
- `README.md`, `agent.md`, `install.md`, `changelog.md` — описание
  проекта, правила для ИИ-агента, работающего в этом репозитории,
  подробная инструкция по установке/настройке/созданию пользователей и
  история изменений соответственно.

### Исправлено

- **Регресс курсора в редакторе**, внесённый переходом на инлайн-
  форматирование: реактивный `dangerouslySetInnerHTML={{ __html:
  block.content }}` заставлял React переустанавливать `innerHTML` живого
  `contentEditable` на каждое нажатие клавиши (новая строка почти всегда
  отличается от предыдущей на один символ, поэтому React считал это
  изменением и сбрасывал DOM), что роняло позицию курсора. Исправлено
  компонентом `EditableBlockContent` (`apps/web/components/Editor.tsx`) —
  синхронизация DOM ↔ state сделана императивно через `ref` + `useEffect`
  со сверкой перед записью, а не декларативным пропом.
- **Раздача вложений страниц не работала в принципе.** Роута
  `GET .../pages/:pageId/assets/:fileName`, реально отдающего байты
  файла, не существовало вообще — `<img>` в статьях ссылался на путь,
  который физически ничего не обслуживал. Добавлен сам роут, и заодно
  закрыты смежные дыры в правах: POST этого же роута (загрузка вложения)
  и оба роута истории версий (`GET/POST .../history/...`) проверяли
  только `requireOwnStorageOrShared` (который лишь выставляет флаг, не
  блокирует запрос сам по себе) и не сверяли `sharing[]` страницы — любой
  авторизованный пользователь мог загрузить файл или прочитать/
  восстановить версию чужой страницы, зная её ID, даже без доступа к
  ней. Добавлена проверка `hasAccess(..., 'edit'/'read')` во все
  четыре роута.
- Убран мёртвый код: `filePickerState.kind` выставлялся, но не
  использовался — диалог выбора файла показывал все файлы независимо от
  того, что выбрали в слэш-меню. Теперь `imagesOnly` реально фильтрует
  список.
- Удалён `apps/web/app/shared/view/` — отдельный вьюер расшаренного
  документа, ставший избыточным после того, как главный воркспейс
  научился открывать чужие страницы напрямую через `openPage()`. Раньше
  существовали одновременно два пути рендеринга одной и той же страницы;
  теперь — один.
- **Логин переставал работать после любого перезапуска сервера.**
  Причина: учётные данные (email + хеш пароля) хранились в `Map` в
  памяти процесса, а сами пользователи — на диске; после рестарта диск
  помнил пользователя, а пароль от него — нет. Перенёс credentials в
  `STORAGE_ROOT/auth/credentials.json` через новые методы `FsEngine`
  (`getCredentialByEmail`, `setCredential`, `getAllCredentials`,
  `removeCredentialsForUser`) — теперь переживают перезапуск.
- **`.env` сервера иногда не подхватывался в проде.** `dotenv/config` без
  явного пути ищет `.env` в `process.cwd()`, который зависит от того, как
  именно процесс-менеджер (PM2/systemd/панель хостинга) запускает Node.
  `apps/server/src/index.ts` теперь резолвит путь к `.env` от
  расположения самого файла — не зависит от рабочей директории запуска.
  При старте и при неудачном логине сервер теперь подробно логирует, что
  именно произошло (какой `.env` загружен, какой `ADMIN_EMAIL` ожидается,
  создан администратор или уже существовал, не найден email или неверный
  пароль).
- `seedAdminFromEnv` стал идемпотентным по email (а не по «есть ли вообще
  пользователи в хранилище») — смена `ADMIN_EMAIL` в `.env` и перезапуск
  теперь создают нового администратора с новым email, вместо того чтобы
  молча ничего не делать, если в хранилище уже был кто-то другой.
- `/health` теперь возвращает `adminEmailConfigured` и `webOrigin` — можно
  проверить конфигурацию одним `curl` без браузера и логов.
- **Бэкенд падал при старте**: `SyntaxError: The requested module
  '@core/fs-engine' does not provide an export named 'FsEngineError'`.
  Причина — у пакетов `packages/core-auth`, `core-fs-engine`,
  `core-realtime`, `core-chat`, `core-webrtc` не было `"type": "module"`
  в `package.json` (было только у `apps/server`), поэтому Node/tsx
  собирал их исходники как CommonJS, а `export * from './types.js'`
  превращался в динамический реэкспорт, который Node не может статически
  разобрать при именованном `import`. Добавлено `"type": "module"` во
  все пять `package.json` пакетов.
- **Next.js не подхватывал `PORT` из `apps/web/.env.local`.** CLI Next.js
  читает `.env`-файлы уже после выбора порта listener'а, то есть простая
  запись `PORT=3040` в `.env.local` ни на что не влияла. Исправлено
  новым `apps/web/scripts/run.mjs`, который загружает `.env.local`
  вручную и передаёт порт явным флагом `-p`; `npm run dev`/`npm run
  start` в `apps/web` теперь используют этот скрипт.
- Убраны неявные обращения к глобальному `crypto.randomUUID()` в
  `apps/server/src/routes/auth.routes.ts` — теперь везде явный импорт
  `randomUUID` из `node:crypto`.

### Изменено

- `useUserStore` (Zustand) больше не хранит `user`/`setUser` — это
  ответственность `SessionProvider`. Вместо простого `activePageId`

  `projectId` (моё пространство) / `activeOwnerId`+`activeProjectId`+
  `activePageId` (что сейчас открыто — своё или чужое).
- `Editor` (`apps/web/components/Editor.tsx`) получил проп `readOnly` —
  используется при просмотре расшаренного документа с уровнем доступа

- Корневой `README.md` переписан в сторону чистого описания проекта (что
  это, архитектура, технологии, известные ограничения) — практические
  инструкции по установке в `install.md`.

  перезаписывали уже существующие аккаунты.

## [0.1.0] — первая версия MVP

### Добавлено

- Монорепозиторий (npm workspaces + Turborepo): `packages/core-auth`,
  `packages/core-fs-engine`, `packages/core-realtime`, `packages/core-chat`,
  `packages/core-webrtc`, `apps/server`, `apps/web`.
- `@core/fs-engine` — файловое CRUD-хранилище документов без БД: атомарная
  запись, защита от path traversal, блокировки на конкурентную запись,
  снапшоты истории на каждое сохранение, загрузка вложений, наивный поиск.
- `@core/auth` — JWT-аутентификация, RBAC (`Admin/Team-Lead/Member/Guest`),
  мидлвар изоляции файлового хранилища по пользователю.
- `useDocument` (`apps/web/hooks/useDocument.ts`) — клиентский хук с
  debounce-автосохранением (3 секунды), мгновенным локальным редактированием
  и flush'ем при уходе со страницы.
- Express API: роуты `auth`, `admin`, `storage`, `chats`; централизованный
  обработчик ошибок; rate limiting (60 запросов/мин/пользователь на
  запись документов).
- Next.js SPA: сайдбар с drag-and-drop деревом страниц и поиском, блочный
  редактор со слэш-командами, presence (зелёная точка), светлая/тёмная
  тема, скелетоны при загрузке, toast-уведомления о сохранении.
- `@core/realtime` — presence, трансляция курсора и live-патчей через
  Socket.io.
- `@core/chat` — личные и групповые чаты, треды, ссылки на страницы базы
  знаний внутри сообщений.
- `@core/webrtc` — сигналинг для видеозвонков (до 8 участников, mesh).
