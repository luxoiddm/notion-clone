# agent.md — правила для нейросети, работающей с этим репозиторием

Этот файл — инструкция для ИИ-ассистента (Claude, Copilot, Cursor и т.п.),
который редактирует код в этом репозитории. Человек может это тоже
прочитать, но формулировки рассчитаны на агента, выполняющего задачи
автономно.

## Главное правило: файловая система — только через `@core/fs-engine`

Никогда не пиши код, который делает `fs.readFile` / `fs.writeFile` /
`fs.mkdir` напрямую где-либо, кроме `packages/core-fs-engine/src/*` и
`packages/core-chat/src/*` (у чата своя, отдельная, тоже изолированная
файловая логика). Любой другой модуль — `apps/server`, `apps/web`,
`@core/auth`, `@core/realtime` — должен ходить в хранилище только через
методы `FsEngine`. Если для задачи не хватает метода — добавь его в
`FsEngine`, а не открывай прямой доступ к диску из вызывающего кода.

Причина: только так работает гарантия «пользователь не может достать
файлы другого пользователя» — она держится на том, что все пути строятся
через `joinSafe()`/`assertSafeId()` в одном месте.

## Path safety

Любой новый путь, который трогает диск, обязан пройти через
`joinSafe(root, ...segments)` из `pathSafety.ts`. Никогда не
конкатенируй пользовательский ввод в путь строкой (`root + '/' + userId`).
Любой ID, приходящий из HTTP-запроса, сначала проверяй `assertSafeId()`.

## RBAC

Роли: `Admin > Team-Lead > Member > Guest` (`ROLE_RANK` в
`@core/auth/types.ts`). Правила:

- Новый защищённый роут — всегда через `requireAuth(auth)`, и если нужна
  минимальная роль — `requireRole('...')`.
- Роуты `/api/storage/:userId/*` — всегда через
  `requireOwnStorageOrShared(...)`, и если `req.requiresSharingCheck ===
  true`, обработчик роута **обязан** сам проверить `sharing[]` конкретной
  страницы (пример — `storage.routes.ts`, функция `hasAccess`). Это не
  теоретическое требование: в этом файле дважды находили реальные дыры от
  того, что новый роут (загрузка вложений, история версий) забывал эту
  проверку — `ownerGuard` сам по себе **не блокирует** запрос, а только
  выставляет флаг и передаёт обработчику решать. Заводя новый роут под
  `/:userId/:projectId/pages/:pageId/...` — первым делом добавь проверку
  `hasAccess(...)` с нужным уровнем (`read`/`edit`/`admin`), и только
  потом пиши остальную логику.
- Никогда не добавляй эндпоинт саморегистрации. Единственные способы
  создать пользователя: автосоздание администратора из `ADMIN_EMAIL`/
  `ADMIN_PASSWORD` в `.env` (`seedAdminFromEnv`, вызывается при каждом
  старте сервера и no-op'ается, если хранилище уже не пустое),
  `/api/admin/users`, `/api/admin/invites` + `/api/auth/accept-invite`, и
  ручной запасной `/api/auth/bootstrap-admin` (тоже самоотключается, как
  только в хранилище появляется хотя бы один пользователь — см.
  `FsEngine.hasAnyUsers()`).

## `router` из `next/navigation` — не клади в зависимости эффекта, который сам вызывает `router.replace`/`push`

Поймано на реальном баге: `useRouter()` не гарантированно стабилен по
ссылке между рендерами в App Router. Если эффект и вызывает
`router.replace(...)`, и держит `router` в массиве зависимостей —
получается бесконечный цикл (`replace` → ре-рендер → эффект видит
«router изменился» → `replace` снова → …), с предупреждением React
`Maximum update depth exceeded`. Внешне это выглядело как «кнопки
навигации не реагируют на клик» — не потому что клик блокировался, а
потому что страница была в состоянии постоянного ре-рендера.

Если нужно синхронизировать состояние с URL через `router.replace`:
`router` — не в зависимостях (`// eslint-disable-next-line
react-hooks/exhaustive-deps`, стандартная практика именно для этого
хука), и дополнительно проверяй, что итоговая query-строка реально
отличается от текущей, прежде чем вызывать `replace` — вторая линия
защиты, если эффект всё-таки перезапустится по другой причине.

## Объект-обёртка в возврате хука, пересобираемый каждый рендер — не клади целиком в зависимости

Второй случай `Maximum update depth exceeded` из той же серии — уже не
про `router`. `useDocument()` намеренно возвращает `meta: meta ? {
...meta, title } : null` — новый объект **на каждый рендер**, чтобы
поле всегда показывало живо набираемый заголовок, а не то, что было на
момент последнего сохранения. Эффект где-то ещё, зависевший от
`doc.meta` целиком (не от `doc.meta?.id`/`doc.meta?.title` по
отдельности), видел «объект изменился» на **любом** рендере и
перезапускался безусловно — с любым `setState` внутри это сразу
бесконечный цикл.

Общий урок: если хук возвращает объект-обёртку, пересобираемый на
каждый вызов ради удобства (актуальные вложенные данные без ручного
мёржа у каждого потребителя) — в зависимостях `useEffect`/`useMemo`
клади конкретные примитивные поля этого объекта, не сам объект. Перед
тем как добавить объект/массив в зависимости эффекта, стоит заглянуть в
его источник и проверить, действительно ли он стабилен по ссылке
между рендерами, когда содержимое не менялось — не полагаться на
интуицию.

## changelog.md — вставляй новую запись через `sed`, не через `str_replace`

Поймано на практике **четыре раза подряд** в этом файле — заметка ниже
"будь внимательнее" сама по себе не сработала ни разу, несмотря на то,
что была явно прописана после первого же случая. Механическая причина
одна и та же: `str_replace` с `old_str`, матчащим заголовок
ПРЕДЫДУЩЕЙ версии (`## [Unreleased]\n\n## [X.Y.Z] — дата`), и `new_str`
с новым заголовком — при написании `new_str` раз за разом забывался
старый заголовок в конце, и он просто пропадал из файла (запись
предыдущей версии становится телом новой, без собственного заголовка).
Раз внимательность не помогает — используй вместо этого команду,
которая **физически не может** случайно стереть существующую строку,
потому что не читает и не переписывает её вообще:

```bash
sed -i '/^## \[Unreleased\]$/a\
\
## [X.Y.Z] — ГГГГ-ММ-ДД\
\
### Добавлено\
\
- Текст записи.' changelog.md
```

(`a\` — вставka ПОСЛЕ найденной строки, не замена; строка
`## [Unreleased]` и всё, что после неё, остаются нетронутыми буквально
на уровне файловой системы — сдвигаются вниз, не переписываются). Для
многострочного текста проще: вставить пустую `## [X.Y.Z] — дата`
СРАЗУ после `## [Unreleased]` этим способом, затем ОТДЕЛЬНЫМ
`str_replace` дописать текст записи под уже существующий, не
переписываемый заголовок — `old_str` в этом втором шаге ищет уже
вставленный заголовок НОВОЙ версии (который эта команда только что
создала), не старой, так что случайно стереть чужой заголовок в
принципе негде.

Проверяется одной командой сразу после правки: `grep -n "^## \[1\."
changelog.md | head -6` — должны быть видны ОБЕ версии (новая и
предыдущая) как отдельные заголовки, не одна.

## TypeScript

- **Если `node_modules` реально установлен (`npm install` прошёл) —
  ВСЕГДА проверяй через настоящую команду сборки каждого пакета
  (`cd apps/server && npx tsc -p tsconfig.json --noEmit`, то же для
  `apps/web` и каждого `packages/*`), а не через изолированную
  проверку одного файла с урезанными флагами.** Поймано на реальном
  случае: вся публикация страниц (фича на несколько версий) была
  написана, каждый файл проверен через `tsc --noEmit --skipLibCheck
  <file>` на отдельном файле — и КАЖДЫЙ РАЗ выходило чисто. На деле
  настоящая сборка (`tsc -p tsconfig.json`, с реальным
  `noUncheckedIndexedAccess: true` из `tsconfig.base.json` и полным
  резолвом типов воркспейса) падала с **85 ошибками** — `req.params.x`
  типизируется как `string | undefined`, не `string`, и это касалось
  ВСЕГО кодовой базы, включая файлы, написанные задолго до этой сессии
  (`storage.routes.ts` — 48 ошибок сам по себе). Отдельно нашлось ещё
  две настоящие ошибки типов в `apps/web` (несовместимость
  `React.ComponentType<{size}>` с `lucide-react` при этой версии
  `@types/react`; ref-колбэк, возвращающий `null` вместо `void`) — обе
  тоже пропущены изолированной проверкой. Пользователь тем временем
  честно жаловался, что фича не работает — сервер физически не мог
  собраться, PM2 продолжал крутить старую версию, и никакой из моих
  ответов "проверил tsc, всё чисто" не был правдой в смысле, который
  имеет значение (соберётся ли `npm run build`). Изолированная
  проверка одного файла остаётся полезной как *первая, быстрая*
  проверка синтаксиса по ходу редактирования — но не заменяет
  настоящую сборку перед тем, как сказать "готово" и отдать архив.
  **Конвенция для новых роутов**: `req.params.xxx` — всегда `!` сразу
  после имени (`req.params.pageId!`), не голое обращение — из-за
  `noUncheckedIndexedAccess: true` в `tsconfig.base.json` Express
  типизирует `req.params` через индексную сигнатуру
  (`{[key: string]: string}`), и без `!` любое обращение к
  конкретному параметру даёт `string | undefined`, что не пройдёт
  настоящую сборку. Безопасно ровно потому, что Express гарантирует
  наличие параметра, если маршрут вообще совпал по паттерну — а если
  не совпал, обработчик не вызовется вообще.
- **Проверяй синтаксис через `tsc`, не через подсчёт скобок.** В этой
  среде есть глобальный `tsc` (`which tsc` → `/home/claude/.npm-global/bin/tsc`),
  и `npm install` в `apps/web` может частично дотянуться до registry
  (не всегда — `turbo` из корневого `package.json` уже словил `403`,
  так что полный `node_modules` не гарантирован). Даже без
  `node_modules` `tsc --noEmit --jsx preserve --skipLibCheck --target
  es2022 --module esnext --moduleResolution bundler <file>` на
  отдельном файле реально парсит TS/TSX и ловит настоящие синтаксические
  ошибки (коды `TS1xxx`) — просто не резолвит типы внешних модулей (даст
  `TS2307`/`TS2503`/`TS7006` и подобные, это ожидаемо и не баг). Раньше в
  этом репозитории ревью синтаксиса делалось грубым скриптом, считающим
  `{`/`}`/`(`/`)` как символы — он **ложно** находит "рассинхрон" на
  вполне корректном коде, если в файле есть regex-литералы с
  экранированными или находящимися в `[...]`-классах скобками (```/\(([^)\n]+)\)/``` — три `(` и четыре `)` в исходном тексте, при этом синтаксически всё
  верно). Если очень нужен именно быстрый smoke-тест без `tsc` —
  фильтруй по `error TS1[0-9]{3}:` (`grep -E`, с двоеточием на конце,
  иначе `TS1804` ложно совпадёт внутри `TS18046`) вместо подсчёта
  символов.
- **Осторожно с error-кодами за пределами `TS1xxx` без node_modules** —
  не только "cannot find module" очевидно каскадит из нерезолвящихся
  импортов. Проверено на практике: `Record<ЛитеральныйUnion, T>[key]`
  сам по себе безопасен от `noUncheckedIndexedAccess` (см. правило про
  `BLOCK_TAG`/`BLOCK_CLASS` ниже — это подтверждено изолированным
  тестом), но если тип ключа импортирован из другого пакета
  (`@core/fs-engine`), который не резолвится в одиночной проверке файла,
  TS видит уже не литеральный union, а расплывшийся тип — и тогда
  `TS2532: Object is possibly 'undefined'` вылезает там, где в реальной
  сборке (с установленными зависимостями) его не будет. То же самое с
  `TS7031`/`TS2322` вокруг JSX и `key`/`children`-пропов — почти всегда
  каскад из нерезолвящегося `@types/react`. Тот же `TS7031` вылезает и
  без всякого JSX: колбэки `socket.on('event', ({ a, b }) => ...)` в
  `@core/realtime`, где типы событий завязаны на `Socket<...>` из
  `socket.io` — без резолва этого пакета generic-параметры схлопываются
  в `any`, и деструктурированные параметры каждого колбэка ловят implicit
  any. Общее правило: любой внешний пакет, чьи типы не резолвятся в
  одиночной проверке файла, может утащить за собой в `any` всё, что от
  него дженерик-зависимо — не только React. Если код похож на баг, но
  завязан на тип из другого пакета/библиотеки — прежде чем чинить,
  воспроизведи в отдельном мини-файле с локально продублированным типом
  (без импорта) и проверь, остаётся ли ошибка — так отличаешь настоящую
  проблему от шума.
- `strict: true` везде, `any` под запретом. Если тип реально неизвестен —
  `unknown` + сужение, не `any`.
- Каждый пакет — ESM (`"type": "module"` **обязательно в `package.json`
  каждого** `packages/core-*` и в `apps/server`, не только у самого
  сервера). Без этого поля Node трактует `.ts`-файлы пакета как
  CommonJS, и звёздочные реэкспорты вида `export * from './types.js'`
  транспилируются в динамическую форму, которую Node не может
  статически проанализировать при именованном `import { X } from
  '@core/...'` — падает с `SyntaxError: does not provide an export
  named 'X'`. Если создаёшь новый пакет в `packages/` — сразу добавь
  `"type": "module"` в его `package.json`, иначе бэкенд не запустится.
- `NodeNext` module resolution. Импорты внутри пакетов — с расширением
  `.js` (даже у `.ts`-файлов), это требование `NodeNext`.
- `noUncheckedIndexedAccess: true` в `tsconfig.base.json` — любое
  `array[i]` или `record[key]` типизируется как `T | undefined`, **если**
  индекс — обычный `string`/`number`, а не литеральный union/точный ключ
  объекта. Разница на практике: `BLOCK_TAG[block.type]`, где `block.type:
  PageBlockType` (литеральный union) и `BLOCK_TAG: Record<PageBlockType,
  string>` — безопасно, TS знает все ключи. А `SOME_MAP[el.tagName]`, где
  `el.tagName: string` (обычная строка, не сужена) — **не безопасно**,
  вернёт `T | undefined` и не скомпилируется при прямом использовании.
  Если нужно замапить произвольную строку (DOM-тег, введённый пользователем
  ключ и т.п.) — используй `switch`/`if`-цепочку с явными литералами
  вместо lookup-объекта, либо деструктурируй с проверкой на `undefined`
  (`const [first] = arr; if (!first) return;`), а не `arr[0].prop` напрямую.
- Публичный API пакета — только то, что реэкспортировано из его
  `src/index.ts`. Не импортируй внутренние файлы другого пакета напрямую
  (`@core/fs-engine/src/FsEngine` вместо `@core/fs-engine`).

## Порты и `.env`

Next.js **не читает** `PORT`/`-p` из `.env`/`.env.local` сам по себе —
файлы окружения framework подхватывает уже после старта CLI, когда порт
слушателя уже выбран. Поэтому `apps/web` запускается не напрямую через
`next dev`, а через `apps/web/scripts/run.mjs`, который сам загружает
`.env.local` и передаёт `-p <PORT>` явно. Если меняешь способ запуска
web-приложения — не убирай этот скрипт, иначе порт снова тихо откатится
на 3000. Подробности — в [install.md](./install.md#порты).

`apps/server`, наоборот, читает `.env` штатно — но не через
`process.cwd()`-зависимый `dotenv/config`, а явно резолвя путь
относительно расположения `src/index.ts`. Так `.env` находится независимо
от того, из какой рабочей директории процесс-менеджер (PM2, systemd,
панель хостинга) запускает Node — это реальная причина, по которой
переменные из `.env` иногда «не подхватывались» в проде. Если переносишь
`index.ts` в другое место — не возвращай `import 'dotenv/config'` без
явного пути, это откатит фикс.

**Важно про `here` vs `serverRoot`**: `here = path.dirname(fileURLToPath(import.meta.url))`
— это директория САМОГО файла (`apps/server/src`, на уровень глубже, чем
нужно), поэтому сразу вычисляется `serverRoot = path.resolve(here, '..')`
(= `apps/server`), и именно от `serverRoot` резолвятся и `.env`, и
`STORAGE_ROOT` (`path.resolve(serverRoot, process.env.STORAGE_ROOT ??
'./storage')`). Раньше `STORAGE_ROOT` по ошибке резолвился напрямую от
`here` (без ухода на уровень выше) — из-за этого хранилище создавалось
внутри `apps/server/src/storage` вместо `apps/server/storage`. Тот же
паттерн (`here` → `serverRoot` → `.env`/`STORAGE_ROOT`) используется в
`apps/server/scripts/reset-admin.ts`, только там `here` = `apps/server/scripts`.
Если добавляешь ещё один файл, читающий `.env`/`STORAGE_ROOT` напрямую —
всегда используй `serverRoot`, никогда не `here`.
Дефолт (`./storage`) кладёт хранилище внутрь проекта
(`apps/server/storage/`), а не во внешний системный путь вроде
`/var/data/...` — так и было запрошено. Абсолютный `STORAGE_ROOT`
по-прежнему работает как есть (`path.resolve()` игнорирует базу, если
второй аргумент уже абсолютный).

## Порядок инициализации сервера (`apps/server/src/index.ts`)

Не своди `httpServer`/`io`/`app` обратно к простому `createServer(app)` —
там намеренно другой порядок из-за циклической зависимости: `io` нужен
`httpServer` (для сокетов), а Express-`app` нужен уже готовый `io`
(`chatRoutes` эмитит `chat:message` через него). Поэтому: сначала голый
`createServer()` без обработчика, потом `initRealtime({ httpServer, ... })`
строит `io`, потом `createApp({ ..., io })` строит Express-приложение, и
только в конце `httpServer.on('request', app)` навешивает его как
обработчик запросов. Если добавляешь ещё один модуль, которому нужен и
`io`, и HTTP-роуты одновременно — используй эту же последовательность, а
не `createServer(app)` в начале.

## Reverse proxy

`deploy/nginx.conf` — эталонный конфиг для продакшена (один домен, роутинг
на `apps/web` и `apps/server`, отдельный `location /socket.io/` с
апгрейдом до WebSocket). Если меняешь пути API или добавляешь новый
внешний порт/процесс — обнови и его, иначе инструкция по продакшену в
install.md разойдётся с реальным поведением.

## Изменения — обязательно фиксируй в changelog.md

Любое пользователю видимое изменение (новый эндпоинт, изменение схемы
данных на диске, новая переменная окружения, breaking change в API
пакета) добавляй записью в [changelog.md](./changelog.md) в формате
Keep a Changelog, в раздел `[Unreleased]` наверху файла. Не переписывай
и не удаляй прошлые записи.

## Версия — где живёт, как менять

`version` в `package.json` (корень + `apps/server` + `apps/web`, все
три держи синхронными) — это то, что видно пользователю (экран входа,
страница настроек, админ-панель, `GET /health`) через
`apps/server/src/index.ts`'s `APP_VERSION`, прочитанный из
`apps/server/package.json` при старте процесса и прокинутый в
`GET /api/site-settings`. Это НЕ поле в `site-settings.json` —
осознанно: версия — свойство того, какой код развёрнут, не то, что
администратор настраивает, и не должна быть перезаписываемой через
`PATCH /api/admin/site-settings`.

Бампай версию (semver) при каждом добавленном функционале — не жди
накопления, бампай по завершении etap'а/фичи, отдельно от чисто
багфиксов без нового функционала (те можно копить). Новая
функциональность — MINOR (`1.1.0` → `1.2.0`), просто исправление без
новых возможностей — PATCH, breaking change — MAJOR. Когда бампаешь:
обнови все три `package.json` одинаково, и в `changelog.md` преврати
`[Unreleased]` в `[X.Y.Z] — <дата>` (см. пример превращения в `1.0.0`),
начав пустой `[Unreleased]` заново над ним — не переписывай уже
зафиксированные версии задним числом. Финальный архив для пользователя
называй по номеру версии (`notion-clone-vX.Y.Z.zip`), не голым
`notion-clone.zip`.

## Rate limiting и безопасность

- **`site.routes.ts` — единственный роут без `requireAuth` во всём
  проекте, и это осознанное, а не забытое исключение.** До него ВООБЩЕ
  каждый роут сидел за проверкой токена — если добавляешь новый роут и
  тянешься скопировать структуру с чего-то существующего, `requireAuth`
  почти наверняка должен остаться. Публичным роут может быть только
  если он (а) отдаёт данные, нужные ДО входа в систему (единственный
  реальный прецедент сейчас — название/логотип сайта для экрана логина)
  и (б) не отдаёт ничего чувствительного (email, роли, содержимое
  документов — ничего такого через публичный роут не отдавать). Запись
  в такой роут не может быть публичной вообще — `site.routes.ts` только
  читает, `PATCH`/`POST` для него сидят в `admin.routes.ts` за
  `requireRole('Admin')`, как обычно.
- Любой новый роут, создающий/меняющий документы, вешай за
  `documentWriteLimiter` (60 запросов/мин/пользователь), а не за
  `readLimiter`.
- Не логируй пароли, токены или содержимое `ACCESS_TOKEN_SECRET` /
  `REFRESH_TOKEN_SECRET`. Ошибки логируй через `errorHandler.ts` — он уже
  различает `FsEngineError` (со стеком и `cause`) и прочие ошибки.
- Не хардкодь секреты в код — только через `process.env`. Если добавляешь
  новую обязательную переменную окружения, обнови оба `.env.example`
  файла и `install.md`.
- **Вступление в комнату сокета — тоже точка доступа, не только HTTP-роуты.**
  `chat:join` в `@core/realtime` проверяет членство через `isChatMember`
  перед тем, как реально добавить сокет в комнату — иначе можно было бы
  подписаться на чужой чат, просто зная/угадав `chatId`, в обход всех
  проверок на REST-эндпоинтах. Если добавляешь новую комнату для
  какого-то ещё ресурса — заводи для неё такую же проверку, а не только
  полагайся на то, что HTTP-запросы защищены. (Есть отступление от этого
  правила: `page:join` пока пускает в комнату presence любого
  аутентифицированного пользователя без проверки прав на страницу — это
  утечка низкой критичности, «кто сейчас смотрит страницу N» без доступа
  к её содержимому, но не идеал; если руки дойдут, тот же паттерн
  `isChatMember` стоит повторить и там.)
- **Каждый роут `chat.routes.ts`, принимающий `:chatId`, обязан явно
  проверить `summary.memberIds.includes(req.user!.id)`** — это НЕ дано по
  умолчанию просто потому, что роутер сидит за `requireAuth`
  (аутентификация ≠ авторизация на конкретный чат). При ревью нашёлся
  реальный пример: `GET /:chatId/threads/:threadRootId` эту проверку
  пропускал, и любой аутентифицированный пользователь мог прочитать
  ответы в треде чужого чата, просто зная `chatId`. `POST
  /:chatId/messages` защищён иначе — проверку делает не сам роут, а
  `ChatEngine.sendMessage()` изнутри — тоже валидно, но если копируешь
  структуру нового роута с оглядкой на этот, не забудь, что проверка там
  спрятана на уровень ниже, а не рядом с остальными.
- **Тот же класс дыры нашёлся в третий раз — теперь в `@core/webrtc`.**
  `call:start`/`call:join` изначально принимали голый `chatId` без
  проверки членства (то же, что было у `chat:join` в `@core/realtime`, и
  у пары роутов `storage.routes.ts` до этого). Если добавляешь ещё одну
  фичу, завязанную на `chatId` или `pageId` — сокет-событие, REST-роут,
  что угодно — проверка членства/доступа идёт в чек-лист по умолчанию,
  а не «добавим, если найдём дыру при ревью». Заодно там же нашлись два
  соседних бага той же природы (не про доступ, но из той же категории
  «работает только в happy path»): `call:start` не был идемпотентным
  (повторный вызов затирал уже идущий звонок) и не было очистки по
  `disconnect` (только по явному `call:leave`) — оба чинятся так же, как
  `PresenceStore.leaveAll` в `@core/realtime` уже делает для presence.

## Редактор (`apps/web/components/Editor.tsx`)

Собственная реализация на `contentEditable`, не Lexical/Slate. Контент
блока хранится как санитизированный inline-HTML (`PageBlock.content`),
не голый текст — инлайн-форматирование (bold/italic/strike/code/link)
работает через `document.execCommand` + ручную обёртку `Range` для кода.

**Не возвращай `dangerouslySetInnerHTML={{ __html: block.content }}`
напрямую на элемент, реактивно завязанный на state.** Раньше так и было
сделано, и это ломало курсор на каждое нажатие клавиши: `handleInput`
обновляет state при каждом вводе → новый `__html` не совпадает с
предыдущим (контент вырос на символ) → React переустанавливает
`innerHTML` в живом DOM → сбрасывается selection. Текущее решение —
`EditableBlockContent`: `ref` + `useEffect`, который трогает
`el.innerHTML` только если он **отличается** от `block.content` (то есть
контент изменился не из-за ввода этим же элементом — сменился тип блока,
вставился файл, сработала кнопка форматирования). Если добавляешь новую
фичу, меняющую содержимое блока программно (не через ввод пользователя),
делай это через `updateBlock(...)`, а не прямой манипуляцией DOM в обход
`block.content` — иначе `useEffect`-проверка не увидит изменение.

Любой новый способ превратить пользовательский ввод в HTML (не только
через `execCommand`) обязан пройти через `sanitizeInlineHtml()`
(`apps/web/lib/sanitize.ts`) перед `updateBlock(...)`. Это allowlist по
тегам, а не blocklist — новый разрешённый тег добавляй в
`ALLOWED_TAGS`, а не ослабляй проверку иначе. Помни, что это
client-side-only защита (см. README «Известные ограничения»); при
переносе на сервер — дублируй ту же проверку в
`FsEngine.savePageContent`, а не полагайся только на клиент.

## Файловое хранилище

Два независимых физических места на диске, оба через `FsEngine` — не
путай их, но с этого этапа активно используется только одно:

- **Личное хранилище пользователя** (`FsEngine.saveUserFile`/
  `listUserFiles`, роуты в `files.routes.ts`, манифест
  `users/{userId}/files/manifest.json`) — единственный путь для НОВЫХ
  загрузок, каким бы способом файл ни добавили: перетаскивание,
  вставка из буфера (Ctrl/Cmd+V), команды `/Изображение`/`/Файл`, кнопки
  в тулбаре — все четыре в `Editor.tsx` идут через общую
  `uploadFileAndInsertBlock()`. Переиспользуется между статьями, к нему
  же обращается страница `/files`.
- **`.assets` конкретной страницы** (`FsEngine.saveAsset`/
  `getAssetAbsolutePath`, роут в `storage.routes.ts`) — исходно (первое
  ТЗ) это был путь для перетаскивания файла в статью. **Больше не
  используется для новых загрузок** — `Editor.tsx` про него не знает.
  Оставлен в `FsEngine` и в бэкенде нетронутым ради обратной
  совместимости: у статей, созданных до этого изменения, картинки уже
  физически лежат там, и рендер `<img src={withAuthToken(...)}>` не
  завязан на то, из какого хранилища пришёл URL — так что старый контент
  продолжает открываться без миграции. Не удаляй этот код и роут — просто
  не добавляй в него новых вызовов из фронтенда.

Оба раздают файлы через `res.sendFile(absolutePath)`, и оба используют
`?token=` вместо `Authorization`-заголовка (см. следующий раздел) —
любой новый файл-сервинг роут должен делать так же, иначе `<img>`/`<a>`
в браузере не смогут их загрузить.

## Медиа и `requireAuth` через query-параметр

`<img src>` / `<a href>`, которые браузер запрашивает сам, не может
приложить `Authorization`-заголовок. `requireAuth` в `@core/auth`
принимает токен и как `?token=` в query — используй
`withAuthToken(url)` из `apps/web/lib/api.ts` в любом месте, где строишь
URL для `src`/`href`, ведущий на наш API. Не изобретай отдельный способ
авторизации для новых медиа-роутов — переиспользуй этот же паттерн.

## Один путь рендеринга на фичу, а не два

Когда общая страница `/shared` и общее дерево в сайдбаре научились
открывать чужую страницу прямо в основном воркспейсе (`openPage()` в
`useUserStore` + `useDocument(ownerId, ...)`, где `ownerId` не обязательно
равен текущему пользователю), отдельный read-only роут `/shared/view` стал
дублирующим кодом и был удалён. Урок на будущее: если два UI-пути
рендерят «просмотр документа» — это сигнал объединить их в один
компонент с параметром (`readOnly`, `ownerId` и т.п.), а не поддерживать
оба. Прежде чем добавлять новый экран для чего-то, что уже отображается
где-то ещё, проверь, нельзя ли просто передать нужный контекст в
существующий.

## Перед тем как считать задачу выполненной

1. Новый роут под `/api/storage/:userId/*`, `/api/files/*` — проверил
   `req.requiresSharingCheck` (или эквивалент) на каждом, кто трогает
   чужие данные? В этом репозитории уже трижды находили роуты без этой
   проверки задним числом (загрузка вложений, история версий) — легче
   свериться сразу, чем находить потом.
2. Новый или изменённый роут — есть ли для него хотя бы упоминание в
   `README.md` соответствующего пакета?
3. Если тронул схему данных на диске (`meta.json`, `content.json`,
   `manifest.json`) — обновлён ли раздел «On-disk layout» в
   `packages/core-fs-engine/README.md`?
4. Обновлён `changelog.md`?
5. Если добавил файл/страницу — нет ли уже похожего экрана в другом
   месте, который стоило бы расширить вместо дублирования (см. «Один путь
   рендеринга на фичу» выше)?
